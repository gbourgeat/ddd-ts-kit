# ADR-0003: the in-memory tuple store refuses production

## Decision

The `createTupleStore` that `init --authz rebac` writes (`packages/cli/templates/init/platform/auth/relationships/create-tuple-store.ts.tpl`) answers the in-memory `InMemoryRelationTupleStore` in `development` and `test` only, and throws in any other environment. Its message names what to bind instead: `OpenFgaRelationTupleStore` of `@ddd-ts-kit/openfga`, or a table of the database held to `relationTupleStoreContract`. `InMemoryRelationTupleStore` itself is unchanged and stays free for tests. This is the rule `DevelopmentHeaderAuthenticator` already follows. The entry of the change is `changes/rebac-tuple-store-refuses-production.md`.

The environment is `process.env['NODE_ENV'] ?? 'development'`: an unset `NODE_ENV` counts as development. That is a choice, made to match `loadConfig` (`packages/cli/templates/init/platform/config/load-config.ts.tpl`), which reads `env.oneOf('NODE_ENV', environments, 'development')`. A process started in production with `NODE_ENV` unset therefore gets the in-memory store without a refusal from `createTupleStore`. What stops it elsewhere: with `--authn none`, `loadConfig` itself reports `NODE_ENV must be development or test` when the variable is unset. With another authenticator nothing in the project reports it.

## Why

The tuples of the in-memory store live in the process. A revocation reaches that instance alone, a second instance never sees it, and a restart forgets every grant. In production that is not a degraded mode, it is an access control that does not hold. A project that starts in that state should not run.

Refusing in `createTupleStore` puts the refusal where the choice is made, and its message says what to do. A generated spec proves it.

Reading an unset `NODE_ENV` as development keeps one reading of the variable across the project: the config, the development authenticator and this store agree. A different default here would make one variable mean two things.

## What it costs

- A project on ReBAC that runs in production binds a real store in `createTupleStore`, or its start refuses. `ddd-ts-kit init --force` brings the refusal and its spec.
- An unset `NODE_ENV` in production is not caught by this function. The deployment sets `NODE_ENV=production`.

## What would reverse it

A start that reads `NODE_ENV` once and refuses when it is unset, for every stack, would let the default of `createTupleStore` go to `production` and close the gap above. A persistent store generated by default would make the refusal needless.
