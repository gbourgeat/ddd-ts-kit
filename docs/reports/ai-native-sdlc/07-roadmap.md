# Roadmap: the proposals in three waves

**Summary.** Twenty-three proposals, ordered by what they bring to the four goals of the
product against what they cost, in three waves. Wave 1 is small, mostly files and skill
paragraphs, and gives the kit the playbook's evidence layer: the review policy as a file, the
two sections of `AGENTS.md`, the origin and versions of a story, the fix with a locked
regression spec, the regulated permission profile, the formatter on write, secrets before the
commit, and the eval suite of the plugin, which is the one medium item worth starting now
because the kit is agent configuration. Wave 2 adds the mechanical pieces: code owners
generated, the measures command, the code checked against its design, the optional review and
triage jobs, the pull request taken to green, the intent home, the deploy guide. Wave 3 closes
the loop with production and keeps the headless design pass for last. Effort is `S` (one
session, one pull request), `M` (a few sessions, one or two pull requests), `L` (a milestone).

## For the kit's own repository

The playbook applies to how the kit is built, not only to what it builds:

- P12 is the kit's own continuous evals; its CI already has the pipeline, the secret is the
  only addition.
- A `REVIEW.md` at the kit's root, with a *Compliance* pass against `docs/ARCHITECTURE.md`,
  `changes/README.md` and the rules of `AGENTS.md` (English only, no dashes, no `any`), would
  give `/code-review` and any reviewer the same policy; the kit's `AGENTS.md` already holds the
  commands and the rule that templates, checker and skills change together.
- `## Mistakes seen here` in the kit's `AGENTS.md`, for what agents get wrong in this
  repository (the two TypeScript versions, the subpath entry files of optional peers, the
  French twin of each page).

## What this report leaves out, and why

| Left out | Why |
|---|---|
| a chat-channel responder (Claude Tag) | the identity, the channel and the MCP access are the platform's; the kit's part is the intent and the incident record (P20, P22) |
| deployment, status and rollback as MCP tools shipped by the kit | they depend on the target platform; the kit stops at the image and says so (P19) |
| a detection script and a scheduler | deterministic, tested and specific to the metrics store; the guide gives the queries and the shape (P20) |
| a merge decided by findings | the playbook and the kit both keep a human approval; P15 reports only |
| an agent trailer on by default | many teams refuse attribution lines; P21 makes it a choice |
| per-person productivity measures by default | P23 prints per author only on request, and the guide says why |
| replacing acceptance tests by an agent that exercises the application | the acceptance before the code is stronger than the playbook's verifier; P10 adds the neighbouring flows only |
| `plan.md` as a separate file | the design review per row is the kit's plan, closer to the code and checked by `cited` and P4 |

## Risks

- **Scope creep of the guard.** P7, P11 and P18 all add to the guard; each must stay fast, scoped
  to the file or the command, and fail open, as the guard does today. The sandbox guide stays
  the place that says the guard is not a security boundary.
- **Paid steps in a free pipeline.** P15 and P12 consume API tokens; both follow the `--ci-extras`
  rule and the kit's own CI runs the evals for maintainers' pull requests only.
- **Three hosts.** Every proposal above says what Codex and Copilot run; the ones that need an
  agent of the plugin (P10, the judge in P11) say what the session does without it, as the
  story workflow already does.
- **Documentation debt.** Each pull request carries its guide pages and their French twins;
  the roadmap counts them in the effort.
