# Document the architecture

Scope requested: `$ARGUMENTS` (everything when empty)

Two kinds of content, never mixed in one file:

- **Generated**: derived from the code and the config, regenerated by a command, checked for
  drift in CI, never edited by hand.
- **Written**: decisions and meaning, which no tool can derive. Short, and next to the code it
  explains.

```bash
npx ddd-ts-kit docs            # regenerates everything below marked "generated"
npx ddd-ts-kit docs --check    # CI: fails when a generated file is stale
```

| File | Kind | Source |
|---|---|---|
| `docs/context-map.md` | generated diagram and tables, written rationale | `ddd-ts-kit.config.json`, `CONTEXT.md` files |
| `src/contexts/<ctx>/CONTEXT.md` | written, with generated lists between markers | the team, the scaffolder |
| `docs/integration/event-catalog.md` | generated | `defineIntegrationEvent` declarations, consumers on disk |
| `docs/integration/asyncapi.json` | generated | same |
| `openapi/openapi.json` | generated | route definitions |
| `docs/integration/README.md` | written | integration decisions |
| `docs/adr/NNNN-<slug>.md` | written | one decision each |

## Context map (`docs/context-map.md`)

The generated part, between `<!-- ddd-ts-kit:context-map -->` markers, holds a Mermaid
diagram (one node per context, styled by classification, one arrow per relationship from
upstream to downstream, labelled with the pattern) and a table: context, classification,
purpose (first sentence of its `CONTEXT.md`), upstreams, downstreams, published events.

Write, outside the markers and only when true:

1. **Reading guide**: three lines on how the contexts collaborate for the main business flow.
2. **Why these boundaries**: for each boundary that was debated, the argument that settled it
   (language, autonomy, consistency), in two or three sentences.
3. **Relationship notes**: for every pattern other than `published-language`, why it was
   chosen and what it costs (a conformist accepts upstream changes, a shared kernel needs
   joint ownership).
4. **Known tensions**: boundaries suspected to be wrong, with the signal that would trigger a
   split or a merge.

Do not describe what the diagram already shows.

## `CONTEXT.md`

Six sections, in this order, each short:

- `## Purpose`: two sentences, in business terms. The first one is reused in the context map.
- `## Classification`: `core`, `supporting` or `generic`, and one sentence of why.
- `## Ubiquitous language`: a table of term, meaning in this context, and "not to be confused
  with" when another context uses the same word. Every class, method and event name comes
  from here. Update it in the same change that introduces a name.
- `## Aggregates`: generated list; add one line per aggregate with the invariants it guards.
- `## Published events`: generated list; add for each when it is emitted, in business terms.
- `## Relationships`: upstreams and downstreams with the pattern and what is exchanged.

## Integration documentation (`docs/integration/`)

The catalog and the AsyncAPI document are generated: for each event its type, versions,
payload fields, producer and consumers. Document a payload field with the schema's own
description (`.describe(...)` with zod): it flows into both.

`docs/integration/README.md` is written and answers what the generated files cannot:

1. **Delivery guarantees**: at-least-once, ordering (none across aggregates unless stated),
   what a consumer must tolerate.
2. **Provider**: which event bus adapter runs in each environment, outbox or not, retry and
   dead-letter policy, how to replay.
3. **Versioning policy**: additive inside a version, new version otherwise, how long an old
   version stays published and how its retirement is announced.
4. **Flows**: one short sequence (Mermaid `sequenceDiagram`) per business flow that crosses
   contexts, naming the events in order and the eventual-consistency window users may notice.
5. **External integrations**: for each outside system, the port, the adapter, the
   anti-corruption layer, failure behaviour (timeout, retry, fallback) and where its
   credentials are configured (never their value).

## Decisions

A choice that constrains the future (a boundary, a relationship pattern, a provider, an
exception to a rule) gets an ADR: context, decision, consequences, alternatives rejected, half
a page. Number them, never rewrite an accepted one: supersede it.

## Procedure

1. `npx ddd-ts-kit docs`, read the diff of the generated files: it is the summary of what the
   change did to the architecture.
2. Update the written parts the diff makes stale. If nothing is stale, write nothing.
3. Commit documentation with the code that changed it.
4. `npx ddd-ts-kit docs --check` and `npx ddd-ts-kit check --rule tree/context-doc`.

Style: present tense, business vocabulary, no history of how the code got there, no
duplication of generated content, diagrams in Mermaid so they are diffable.
