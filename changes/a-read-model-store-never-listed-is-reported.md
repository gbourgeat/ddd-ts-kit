**`ddd-ts-kit check` reports a read model store that the list of the read model tables does not answer for (`persistence/read-model-listed`).** The application checks the tables of its read models when it starts, and `npm run db:read-models` before a deployment, by the stores `src/platform/database/read-model-tables.ts` lists and no other: a store written by hand and never listed was checked by nothing, in silence. The new rule, an error, reads the stores of the tree and reports each one the list neither holds under its context (itself, a class that extends it, or an import through a file that re-exports from its file), nor names in `NOT_LISTED`, nor leaves out by a comment between the markers of the file that holds `<context>: <Store>`. Its fix gives the import and the entry to add, the entry alone when the list still imports the class, and for a store the list cannot build, what stands in the way. A store is a class of a context, tests aside, that is not abstract and extends `DrizzleReadModelStore`, `KnexReadModelStore`, `PrismaReadModelStore` or `TypeOrmReadModelStore`, directly or through classes of the project, wherever they are declared. It also reports an entry of the list whose class the file neither imports nor declares, whose import leads to no file, or whose class another context declares; a line of `NOT_LISTED` whose class is gone or whose store `LISTED` answers for; a `LISTED` whose entries it cannot read (spread, or built by a call); and, once, a project on one of the four ORM that holds stores and no list. It does not judge: an abstract class; a store in memory or in a search engine, and a class directly over `TableReadModelStore` of the kernel; a store of the tests; a class declared in a function or in a `namespace` block, and a class expression that has no name of its own (one that has is read under that name); a base that is not the name of the store of the kit or of a class of the project: a namespace (`kit.KnexReadModelStore`), an import alias, a call (`mixin(KnexReadModelStore)`); of two classes of one name in one context, which one an entry names; whether a class that extends a store reads the same table; the reason a comment gives; what a package exports (`ddd-ts-kit explain persistence/read-model-listed`, [docs/concepts/cqrs.md](docs/concepts/cqrs.md#every-table-checked-at-the-start-and-before-a-deployment)).

A comment that leaves a store out counts only between the markers of the file, those of `LISTED` being its place: `init --force` keeps what the markers hold and nothing else, and a comment written elsewhere was lost at the next one, the store then listed. `ddd-ts-kit check <files>` now reports a finding when a file it is repaired in is among those given, not only the file it sits on: an entry removed from the list is reported by the pre-commit hook with the list alone staged. The checker reads what a class extends past a type parameter whose constraint or default holds an object type (`class Totals<Row extends { id: string }> extends Store<Row>`), which it read as extending nothing: every rule that reads a base class now sees that one.

`init` finds the stores by the same reading as the rule, on the sources as the checker reads them and no longer by a regular expression over class declarations. It now reads every source of a context, not its `infrastructure/persistence/` alone, follows a base class declared anywhere under the source root, skips the tests, and no longer takes a class written directly over `TableReadModelStore` for a store kept in a table. It lists a store whose constructor takes `Persistence['database']` or carries `private readonly`, which it named in `NOT_LISTED`; a store its file exports as its default, or does not export, is named there instead of getting an import that does not compile; a list that still imports a class gets its entry back without a second import. Its note says why a store cannot be built, and to write the class that builds it beside the store, in a file of its own, where `init` lists it and `init --force` keeps it: the note of 0.112.0 said to write it in the list file, where `init --force` deletes it.

To move: run `npx ddd-ts-kit check --rule persistence/read-model-listed`. For each store it reports, add to `src/platform/database/read-model-tables.ts` the import and the entry its fix gives (`npx ddd-ts-kit init` writes them), or leave the store out with a comment that holds `<context>: <Store>` and the reason, between the markers of `LISTED`; move there a comment of that kind written elsewhere in the file. For a store the list cannot build, the fix names what stands in the way and gives no entry: write beside the store, in a file of its own, `export class Listed<Store> extends <Store>` with a constructor `(database: <Type>)` or `(database: <Type>, scope: ExecutionScope)` that calls `super(..)`, run `npx ddd-ts-kit init`, which lists that class, then remove the line `'<context>: <Store>'` from `NOT_LISTED`. A project on 0.112.0 that declared such a class in the list file itself, as the note of 0.112.0 said: move the class beside its store and import it before any `init --force`, which rewrites the file outside its markers and would delete it. A project generated before 0.112.0, which has no list: commit, then run `npx ddd-ts-kit init --force`.
