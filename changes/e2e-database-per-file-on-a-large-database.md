**On a PostgreSQL server (`DATABASE_URL`), an end-to-end run of a generated project copies the migrated database once, in a global setup, and each spec file copies the tables of that copy, empty: a large migrated database, many workers and a killed run no longer fail the suite.** Each spec file used to copy the migrated database itself, in the hook that starts the application. Three things followed on a migrated database that holds rows (measured at 474 MB on PostgreSQL 18): a copy takes 6 seconds alone and 46 to 56 seconds when four files copy at once, more than the 30 seconds of a hook; nothing held the pools of the applications under the connections of the server, so workers times 10 connections ended in `too many clients`; and the copies of a run that was killed, or of a file that failed while it started, stayed on the server for an hour, or for good. Now `test/support/test-database-run.ts`, a global setup of the end-to-end run (named by `vitest.e2e.config.ts`, and by `jest.e2e.config.js` when `DATABASE_URL` is set), does once what takes time, where no timeout of a hook applies: it copies the migrated database, one run at a time on the server, and empties the copy, the audit trail included. `cloneDatabase(url)` of `test/support/test-database-clone.ts` copies that template for its file, one copy at a time in a run, in a fraction of a second whatever the migrated database holds. A file therefore starts from the tables of the migrated database and none of its rows, as it does on PostgreSQL in process: what a migration inserts, what an application or a spec left there, never reaches a spec. The tables of the migration tool and of an extension keep their rows. When the emptied tables held more than 64 MB the run says so, with the seconds the copy took and what to do: give the tests a database of their own, migrated and empty. The global setup also reads the connections the server has left (`max_connections`, less what it reserves and what is open, and no more than the connection limit of the role), shares them between the workers of the run, and each application under test opens a pool of that size, 10 at most (`DatabaseClone.poolSize`, handed to the connection of the four ORM; `connectToDatabase` of a project on Drizzle takes a `poolSize` like the three others). Under two connections per file the run is refused before any file starts, with its numbers and the number of workers that fits, for one `8 spec files at once need 16 connections, 2 each at least, and the server leaves 9 (max_connections 20, 3 reserved, 8 open): run at most 4 at once (npm run test:e2e -- --maxWorkers=4), raise max_connections, or state what the run may take (TEST_DATABASE_CONNECTIONS).` `TEST_DATABASE_CONNECTIONS` states the connections the run may take when the server cannot tell (a pooler, other runs to come). A database of a run is named `<database>_test_<run>_template` or `<database>_test_<run>_<random>`, and the run holds an advisory lock keyed by its name from before its first database until its teardown, which drops what is left of its own. The global setup of a run drops the databases named after a run whose lock nobody holds and that nobody is connected to: a run that lives, in another checkout or on another machine, keeps its databases, and a database with any other name is never dropped. A copy that cannot be emptied (tables another role owns) and a migrated database somebody is connected to are refused in the global setup with a message that says what to do. See [the testing strategy](docs/concepts/testing-strategy.md).

To move: these files are written once by `init`, so a project already generated keeps what it has until it takes them by hand. Generate a project with the same flags in a temporary directory (`npx ddd-ts-kit init` with the `stack` of your `ddd-ts-kit.config.json`) and copy from it: `test/support/test-database-run.ts` (new) and `test/support/test-database-clone.ts` (replaced); in `src/platform/database/open-test-database.ts`, the function `openServer`, which now hands `{ poolSize: clone.poolSize }` to its connection; on Drizzle, `src/platform/database/connect-to-database.ts`, for its `poolSize` option; under Vitest, the `globalSetup` line of `vitest.e2e.config.ts`, which names both setups; under Jest, `jest.e2e.config.js` (its `globalSetup` line and the import of `process`), `test/support/test-database-teardown.ts`, and the entry `"test/support/test-database-run.ts"` of the `jest` block of `knip.json`. A spec that read a row a migration inserted stores it itself from now on, as it has to on PostgreSQL in process. The copies an earlier version left carry another name (`<database>_test_<ten digits>_<random>`) and are no longer dropped: list them once with `select datname from pg_database where datname ~ '_test_[0-9]{10}_[0-9a-f]{8}$'` and drop each (`drop database "<name>" with (force)`).
