**Breaking: on a PostgreSQL server (`DATABASE_URL`), an end-to-end run of a generated project copies the migrated database once, in a global setup, and each spec file copies the tables of that copy, emptied but for those the project lists.** Each spec file used to copy the migrated database itself, in the hook that starts the application. Three things followed on a migrated database that holds rows (measured at 474 MB on PostgreSQL 18): a copy takes 6 seconds alone and 46 to 56 seconds when four files copy at once, more than the 30 seconds of a hook; nothing held the pools of the applications under the connections of the server, so workers times 10 connections ended in `too many clients`; and the copies of a run that was killed, or of a file that failed while it started, stayed on the server for an hour, or for good. Now `test/support/test-database-setup.ts`, a global setup of the end-to-end run, opens the run once, where no timeout of a hook applies (`test/support/test-database-run.ts` and the files it is made of, `test-database-session.ts`, `-leftovers.ts`, `-budget.ts`, `-copy.ts`, `-emptying.ts`, `-server.ts`): it copies the migrated database, one run at a time on the server, and empties the copy. `cloneDatabase(url)` of `test/support/test-database-clone.ts` copies that template for its file, one copy at a time in a run, in a fraction of a second whatever the migrated database holds. **What a file finds.** The run empties every table of its copy but those `KEPT_TABLES` lists in `test/support/test-database-kept.ts`, a file of the project: as generated, what the migration tool writes and, with an audit trail, the `audit` schema, which is left as the migrated database holds it. A name is `<schema>.<table>`, or `<schema>.*`, written as the server stores it and without quotes, so in lower case unless the table was created between quotes (`"Countries"` is listed as `public.Countries`); `<schema>.*` keeps every table of the schema whatever its name holds, and a table whose name holds a dot or a quote is kept through it only; any other shape (`*`, `public`, a quoted name, `public.plans.v2`) refuses the run with the shapes a name takes, and a name that is no table of the database (a misspelling, another case, a view) is said in one line, except the names the generated list holds for a table its tool has not created yet. The tables are emptied in one `truncate` without `cascade`, each one alone (`only`): a kept table that references an emptied one refuses the run with both names, a kept table that inherits from an emptied one keeps its rows, and a kept partition of an emptied table, or a kept table that references such a partition, refuses the run with both names. A table another role owns, or one in a schema the role of the run may not use, is left with its rows and named, a table of an extension is left, the materialized views are refreshed, a sequence no column owns keeps its value. The run names on its error output the tables it emptied that held rows, up to 20 of them, and above 64 MB what the copy took; a run with nothing to say writes nothing. **The connections.** The global setup counts the files that run at once, the workers of the run and no more than the files of this run: under Vitest the list of the runner once the filters of the command line are applied, and the share of a shard; under Jest, which hands no list to a global setup, the spec files under `test/` that the patterns of the command line match as Jest matches them, less those `testPathIgnorePatterns` ignores, and the share of a shard. Where the count cannot be made or finds nothing (a run that watches, an empty list, under Jest no spec file under `test/` among those of the run, a pattern that is no expression, no `test/` directory) the workers alone count, so a run is never given more files than it counted. The setup reads what the server has left (`max_connections`, less what it reserves and what is open, and no more than the connection limit of the role), and gives each application under test a pool of its share less one connection to spare, 10 at most (`DatabaseClone.poolSize`, handed to the connection of the four ORM; `connectToDatabase` of a project on Drizzle takes a `poolSize` like the three others). A run that does not fit is refused before any file starts, with its numbers, the number of files at once that fits and what raises the bound that holds it, for one `8 spec files at once need 24 connections (2 for each application at least and 1 to spare), and the role app has 12 left (connection limit 13, 1 open): run at most 4 at once (npm run test:e2e -- --maxWorkers=4), or raise the limit of the role (alter role app connection limit <more>).` `TEST_DATABASE_CONNECTIONS` states fewer connections than the server leaves; a value that is not a whole number, or above what the server leaves, is refused. **What a killed run leaves.** A database of a run is named `<database>_test_<run>_template` or `<database>_test_<run>_<random>`. The run holds an advisory lock keyed by its name, on a session to the `postgres` database of the server, and writes every 15 seconds the time of the server in the comment of its template; its teardown never throws. The global setup of a run drops a database named after a run only when the lock of that run is free, it has not written for a minute and nobody is connected to the database: a run that lives, in another checkout or on another machine, keeps its databases, and a database with any other name is never dropped. **When the server ends a session.** The run takes another session and its lock again at once, and says so when it could not. With its lock again it looks for its template: when that one is gone (the run had no session for more than a minute and another run dropped what it held dead, or an administrator did), it says that it lost its databases, and each file that then cannot copy the template fails with that sentence instead of the `template database ... does not exist` of the server. The copy of the migrated database has a session of its own: when the server ends it, what is left of the copy is dropped and the copy made once more, and a second end is said as such. A statement of the run that somebody cancels (`pg_cancel_backend`) is no ended session: the run says that its copy was cancelled and does not take it again. **The timeouts of the role.** The sessions of the run itself, the one of its lock and those that copy, empty and drop its databases, set `statement_timeout`, `lock_timeout` and, from PostgreSQL 17, `transaction_timeout` to 0 for themselves: a role is given such a timeout (`alter role <role> set statement_timeout = '30s'`) for the requests of an application, and what the run does lasts as long as the database is large. The pool of the application under test keeps the timeouts of its role. The address is the server itself, not a pooler in transaction mode, and `DATABASE_URL` cannot name the `postgres` database: the run says so. **Outside an end-to-end run** (`openTestDatabase(url)` in a spec of the unit run, a project without an HTTP stack), the call opens a run of its own, which copies and empties the migrated database itself. Nothing counts the files that do so at the same time: each opens a small pool, 4 connections at most, and is refused when the server has no room for it at that moment. **Any way of starting the runner.** The files directly under `test/support/` import one another by a relative path (`./test-database-run`), since a runner loads its global setup before any alias exists: the setup loads however the runner is started, and the scripts are the ones a project on Jest had. The spec files of a project on Jest are ES modules, as before: a bare `npx jest -c jest.e2e.config.js` fails with `Must use import to load ES Module`, and `NODE_OPTIONS=--experimental-vm-modules npx jest -c jest.e2e.config.js`, or the runner of an editor given that variable, starts the run as the scripts do. Under `"importExtension": "js"` that path ends with the `.ts` of the source, which the transform of the runner finds, and `init` writes `"allowImportingTsExtensions": true` and `"noEmit": true` in `tsconfig.json`, which let the type check read it, and both as `false` in `tsconfig.build.json`: the build emits what it emitted before. See [the testing strategy](docs/concepts/testing-strategy.md).

To move: these files are written once by `init`, so a project already generated keeps what it has until it takes them. Commit everything first, then run `npx ddd-ts-kit init --force` and read `git diff` before you commit again: it rewrites from the templates of this version every file `init` owns, not the test support alone, and an edit made by hand in one of them is lost. That is all of `src/platform/**`, `test/e2e/support/*`, `test/support/*`, `scripts/*`, the configurations of the runner, of Stryker, of ESLint, of the ORM and of lefthook, `tsconfig.json`, `.github/actions/setup`, the Dependabot configuration, `test/architecture/extractable.spec.ts`, the declarations file of each context, `docs/behaviour/*.md`, and the scripts of `package.json` that `init` generates, whose names are written again: a script you changed under one of those names is replaced, one you added under another name stays. It keeps the workflows, `README.md`, `AGENTS.md`, `CLAUDE.md`, `src/main.ts`, the migrations, the spec files, the API documents, the published language, and a `test/support/test-database-kept.ts` that exists: once written, that file is the project's ([Migrate after a kit upgrade](docs/guides/commands.md)). To take the files one by one instead, generate a project with the same flags in a temporary directory and copy `test/support/test-database-*.ts`, the function `openServer` of `src/platform/database/open-test-database.ts`, `src/platform/database/connect-to-database.ts` on Drizzle, the `globalSetup` line of `vitest.e2e.config.ts` or of `jest.e2e.config.js`, and under `"importExtension": "js"` the `allowImportingTsExtensions` and `noEmit` lines of `tsconfig.json` and of `tsconfig.build.json`; the rule `imports/alias-only` of this version lets those files import one another by a relative path. Then read `test/support/test-database-kept.ts`: add each table whose rows a migration inserts and the application reads at boot or in a request (a spec that read such a row found it until now); write the table of the migration tool under its name when the project gives it one (`tableName`, `migrationsTableName`, `migrations.table`); on Drizzle and TypeORM, a table the ORM does not declare was never emptied by `reset()` and is emptied now, unless listed. The audit trail is not emptied: a migrated database that holds audit rows hands them to every file, as before. Point `DATABASE_URL` at the server itself and at a database other than `postgres`. The copies an earlier version left carry another name (`<database>_test_<ten digits>_<random>`) and are no longer dropped: list them once with `select datname from pg_database where datname ~ '_test_[0-9]{10}_[0-9a-f]{8}$'` and drop each (`drop database "<name>" with (force)`).
