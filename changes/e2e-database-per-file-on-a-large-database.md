**Breaking: on a PostgreSQL server (`DATABASE_URL`), an end-to-end run of a generated project copies the migrated database once, in a global setup, and each spec file copies the tables of that copy, emptied but for those the project lists.** Each spec file used to copy the migrated database itself, in the hook that starts the application. Three things followed on a migrated database that holds rows (measured at 474 MB on PostgreSQL 18): a copy takes 6 seconds alone and 46 to 56 seconds when four files copy at once, more than the 30 seconds of a hook; nothing held the pools of the applications under the connections of the server, so workers times 10 connections ended in `too many clients`; and the copies of a run that was killed, or of a file that failed while it started, stayed on the server for an hour, or for good. Now `test/support/test-database-setup.ts`, a global setup of the end-to-end run, opens the run once, where no timeout of a hook applies (`test/support/test-database-run.ts` and the files it is made of, `test-database-session.ts`, `-leftovers.ts`, `-budget.ts`, `-emptying.ts`, `-server.ts`): it copies the migrated database, one run at a time on the server, and empties the copy. `cloneDatabase(url)` of `test/support/test-database-clone.ts` copies that template for its file, one copy at a time in a run, in a fraction of a second whatever the migrated database holds. **What a file finds.** The run empties every table of its copy but those `KEPT_TABLES` lists in `test/support/test-database-kept.ts`, a file of the project (`<schema>.<table>`, or `<schema>.*`): as generated, what the migration tool writes and, with an audit trail, the `audit` schema, which is left as the migrated database holds it. The tables are emptied in one `truncate` without `cascade`: a kept table that references an emptied one refuses the run with both names. A table another role owns is left with its rows and named, a table of an extension is left, the materialized views are refreshed, a sequence no column owns keeps its value. The run names on its error output the tables it emptied that held rows, and above 64 MB what the copy took. **The connections.** The global setup counts the files that run at once (the workers of the run, and no more than its spec files), reads what the server has left (`max_connections`, less what it reserves and what is open, and no more than the connection limit of the role), and gives each application under test a pool of its share less one connection to spare, 10 at most (`DatabaseClone.poolSize`, handed to the connection of the four ORM; `connectToDatabase` of a project on Drizzle takes a `poolSize` like the three others). A run that does not fit is refused before any file starts, with its numbers, the number of files at once that fits and what raises the bound that holds it, for one `8 spec files at once need 24 connections (2 for each application at least and 1 to spare), and the role app has 12 left (connection limit 13, 1 open): run at most 4 at once (npm run test:e2e -- --maxWorkers=4), or raise the limit of the role (alter role app connection limit <more>).` `TEST_DATABASE_CONNECTIONS` states fewer connections than the server leaves; a value that is not a whole number, or above what the server leaves, is refused. **What a killed run leaves.** A database of a run is named `<database>_test_<run>_template` or `<database>_test_<run>_<random>`. The run holds an advisory lock keyed by its name, on a session to the `postgres` database of the server, and writes every 15 seconds the time of the server in the comment of its template; when the server ends that session the run takes another one and its lock again at once, and its teardown never throws. The global setup of a run drops a database named after a run only when the lock of that run is free, it has not written for a minute and nobody is connected to the database: a run that lives, in another checkout or on another machine, keeps its databases, and a database with any other name is never dropped. The address is the server itself, not a pooler in transaction mode, and `DATABASE_URL` cannot name the `postgres` database: the run says so. **Outside an end-to-end run** (`openTestDatabase(url)` in a spec of the unit run, a project without an HTTP stack), the call opens a run of its own, which copies and empties the migrated database itself. Under Jest the global setup imports its files by alias, which Jest does not resolve there: the `test:e2e` and `ci:test:e2e` scripts start Jest under tsx (`node --import tsx --experimental-vm-modules node_modules/jest/bin/jest.js ...`). See [the testing strategy](docs/concepts/testing-strategy.md).
