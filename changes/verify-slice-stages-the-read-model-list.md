**`ddd-ts-kit verify-slice` stages the list of the read model tables a slice joined.** `generate read-model` adds the store of the read model to `src/platform/database/read-model-tables.ts`, the list the application checks when it starts and `db:read-models` before a deployment. `verify-slice` put that file under "left out, never stage" whatever the ORM, so a worker committed a slice whose read model was absent from the list: its table was never checked, and nothing said so. The file is now staged with the slice when every line changed since `HEAD` belongs to the context, as the schema index is: the import of a store of the context, its entry `['<context>', <Store>]`, read under its alias when another context holds a store of that name, and the name of the context among those an entry may bear. A line is read in the version that holds it, so the list a slice took its own read model away from is staged too, and an import is read by the module it names: the store of the same name of another context, a store of the slice listed under another context, or a package of the kit that bears the name of a context (`@ddd-ts-kit/kernel` beside a context `kernel`) is not of the slice. A list that also holds a change of another context, or of the platform, stays left out: a person decides about it. So does a list that names a context created in the same branch, which `ddd-ts-kit.config.json`, never staged with a slice, does not hold in the last commit: committed alone it would fail `check`, so it waits for the configuration.

To move: nothing. A slice committed without its line in the list gets it back with `ddd-ts-kit init`, which lists the read model stores of the tree.
