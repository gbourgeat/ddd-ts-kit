**The pin of a worker's scope follows the worker.** The guard of the plugin kept the pin of a `context-builder` (its context and its worktree, recorded at its first call) and the count of its run in the checkout the call started in; they are now kept under the git directory the worktrees of the repository share (`ddd-ts-kit/guard/` there), so a call is judged against the worktree pinned whichever checkout it starts in, and the refusal in the worktree of another worker now says how to go on: `cd <worktree> && ...`. Where several workers have a worktree, a first command that names none no longer pins the worker to the worktree its session happens to stand in: it reads, and what it writes is refused with "Run it as `cd <worktree> && ...`" until a command names its worktree, or an editor tool a file under it; a read under another `HOME`, `PATH`, `GIT_DIR`, `TMPDIR` or `CDPATH` is refused there as it is to a pinned worker. With one worker, or outside a git repository, nothing changes. The note taken before a command is compared with the checkout of the session it was taken for, wherever the next call starts: a session whose working directory moved is no longer told that packages or files changed in a checkout the note never read.

A pin that stands and cannot be read, of this version or of an earlier one, holds every call of its worker, which is told to ask the conductor for a new launch: a worker is never pinned twice.

To move: nothing in a project. A worker running while the plugin is updated keeps its pin: the guard finds the one the earlier version took under `.ddd-ts-kit/guard/` and keeps it with the others, for the worktree it names; the old `scope-*.json` and `turns-*.json` files there are removed by the guard a week later.
