**Breaking: under `"importExtension": "js"`, `imports/alias-declared` reports a `tsconfig.json` that does not let the type check read the `.ts` by which a file of `test/support/` names its neighbour, and a `tsconfig.build.json` that would then write nothing.** The files a test runner loads as its global setup import one another by `./<name>.ts` in such a project. The compiler refuses that ending (`TS5097`) unless `tsconfig.json` sets `"allowImportingTsExtensions": true`, which it accepts only in a configuration that emits nothing (`"noEmit": true`), and a `tsconfig.build.json` that extends it without setting both back to `false` compiles without an error and writes no file: `build-aliases` then finds no output, or rewrites an earlier one. `init --import-extension js` writes those four lines, and `ddd-ts-kit check` now holds them: it reports `tsconfig.json` when a file directly under `test/support/` names a neighbour by its `.ts` and neither `allowImportingTsExtensions` nor `rewriteRelativeImportExtensions` is set there, and `tsconfig.build.json` when it inherits `noEmit` or `allowImportingTsExtensions` as `true`. Each finding names the lines to write in both files. The compiled output is what it was: no option rewrites an import of the sources, so no helper is added to it. A project that writes its imports without an extension (`"importExtension": "none"`, the default) is not concerned. See [Import aliases](docs/tools/import-aliases.md).

To move: `npx ddd-ts-kit check --rule imports/alias-declared` lists the two files when they are concerned. Write `"allowImportingTsExtensions": true` and `"noEmit": true` under `compilerOptions` in `tsconfig.json`, and `"compilerOptions": { "allowImportingTsExtensions": false, "noEmit": false }` in `tsconfig.build.json`, or let `npx ddd-ts-kit init --force` write both files after a commit. A script of your own that emits with `tsc -p tsconfig.json` now writes nothing: point it at `tsconfig.build.json`.
