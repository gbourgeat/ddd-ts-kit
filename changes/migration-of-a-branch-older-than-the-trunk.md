**`verify-merge` fails on a migration of a branch that sorts before the last migration of the trunk, on the four ORM, and `merge-trunk --to-land` reorders it on a branch that already holds the trunk.** A branch that lives more than a day holds a migration generated before the last one the trunk gained meanwhile. The migrator of Drizzle then skips it without a word on a database that already applied the later one, and a merge that keeps the journal of the trunk loses its entry; knex, Prisma and TypeORM run it late, so a database that follows the trunk and a new one run one history in two orders. Without a `<commit>`, `ddd-ts-kit verify-merge` now reads the migrations of the working tree against the trunk (the base of the worker, else `origin/HEAD`, else `origin/main`) and exits 1, naming the migration, the last one of the trunk and the command that brings the order right: under drizzle-kit an entry of the journal generated before the last entry of the trunk, or a `.sql` file the journal does not list (`ddd-ts-kit merge-trunk`, or the `meta/` of the trunk then `ddd-ts-kit drizzle-generate --replay` once the trunk is merged otherwise); under knex, Prisma and TypeORM a name that sorts before the trunk's last (`ddd-ts-kit merge-trunk --to-land`). `--warn`, which the pre-push hook of a generated project passes, still softens what a merge lost and never this: the push stops. A working migration (`working-<what-it-does>`) is left out, its place being decided when the branch lands. `merge-trunk --to-land` on a branch that already holds the trunk used to answer that there was nothing to merge: it now lands the migrations all the same (replayed under drizzle-kit, renamed after the last of the trunk elsewhere, stopping when a later migration of the trunk changes the same table) and leaves them to commit. `npm run db:generate <name>` refuses a name a migration of the folder already carries on knex, Prisma and TypeORM too, as it did on Drizzle. The JSON of `verify-merge` gains `migrations`, counted in `errorCount`. The order is read from the files and from git, not measured against a database: see "Migrations: names, merges and order" of `docs/tools/persistence.md`.

To move: run `git fetch`, then `npx ddd-ts-kit verify-merge` on each open branch; a branch it reports follows the command it names before its next push (`npx ddd-ts-kit merge-trunk` under Drizzle, `npx ddd-ts-kit merge-trunk --to-land` under knex, Prisma and TypeORM, then commit the renamed migrations when the branch already held the trunk). A script that reads the exit code of `verify-merge --warn` as always 0 now gets 1 on such a migration. A migration to generate under a name already taken gets a name of its own.
