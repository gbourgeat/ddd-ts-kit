**Breaking: an upload says the text it takes and the content rule of each media type, and a declaration that could receive no file is refused.** Two defects of the content check of `@ddd-ts-kit/kernel` and `@ddd-ts-kit/http`. A text upload passed only as valid UTF-8, so a CSV exported in Windows-1252 or ISO-8859-1 (a bank statement, a spreadsheet) was answered 415: `UploadSpec` and `ContentExpectation` take `text: 'single-byte'`, under which UTF-8 and every single-byte encoding that extends ASCII pass, while a binary file under the name of a CSV is still refused (a signature, a NUL, a control character other than tab, line feed, form feed and carriage return) and so are UTF-16 and UTF-32. The default stays `utf-8`: the bytes cannot say their encoding, and a route that reads UTF-8 must not receive, without a refusal, a file it decodes wrong. The kit never decodes: the handler and the storage get the bytes as sent, and the new `isUtf8(bytes)` of the kernel tells a reader which decoder to take. And `mediaTypes` accepted types the content check then always refused (`application/vnd.ms-excel`, which a browser on Windows sends for a CSV, `application/csv`, `application/octet-stream`): every accepted type now has a content rule, the one of the kit (`contentRuleOf`: a signature for `SIGNED_MEDIA_TYPES`, text for `TEXT_MEDIA_TYPES`, which gain `application/csv` and `text/tab-separated-values`) or the one the upload states in `contentRules`, `text` (text under another name) or `unchecked` (the bytes are taken as they are). A rule stated for a family (`{ 'image/*': 'unchecked' }`) never reaches a type a browser runs when it opens it (`NAMED_ONLY_MEDIA_TYPES`: `image/svg+xml`, `text/html`, `application/xhtml+xml`, `text/javascript`, `application/javascript`): an upload takes one only by naming it. A type with no rule, a family none of whose types has one (`video/*`), an entry that is no media type (`*/*`) and a stated rule that does nothing are refused when the route is declared, by `@Controller`, `defineRoute` and the routes of a Nest controller, with the type and the rules it may state; `FileStaging.uploadUrl` takes `text` and `contentRules`, keeps them in the `PendingUpload` that `confirm` applies, and throws on the same defects (`contentRuleDefects`). The new rule `files/upload-content-rule` of `ddd-ts-kit check` reports them on the line of the type, in a `*.route.ts` or a `*.controller.ts` whose `mediaTypes` and `contentRules` are written as literals. The OpenAPI document says both (`x-text`, `x-content-rules`, and the description of the file). See `docs/concepts/file-storage.md`, "What a route accepts: a content rule for each media type".

To move: run `ddd-ts-kit check --rule files/upload-content-rule` to list the uploads that accept a media type with no content rule; they never received a file of it, and now refuse to start. For each, state the rule: `contentRules: { 'application/vnd.ms-excel': 'text' }` for the CSV of a browser on Windows, `{ 'application/octet-stream': 'unchecked' }` for bytes the route takes as they are, or remove the type. A list built in a constant is not read by the rule: the application says it at start. Add `text: 'single-byte'` to an upload that receives text files which are not UTF-8, and decode them where they are read (`new TextDecoder(isUtf8(bytes) ? 'utf-8' : 'windows-1252')`). A part declared `application/csv` or `text/tab-separated-values` on a route that accepts it, or `text/*`, is now held to the text rule and passes, where it was refused.
