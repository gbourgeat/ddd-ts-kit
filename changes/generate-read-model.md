**`ddd-ts-kit generate read-model <context> <Name>` writes the read model a projection keeps.** `generate projection` wrote the projector alone, and the port of its read model, its table, its store adapter and its fake were written by hand from the declarations of the packages. The new kind writes them: the port in `application/ports/<name>.port.ts` (the type `<Name>Row`, the criteria `<name>Criteria` and the abstract class `<Name>` over `ReadModelStore<<Name>Row>`), the table in the schema of the context, the store adapter `infrastructure/persistence/<orm>-<name>.repository.ts` over the read model store of the ORM package (Drizzle, Knex, Prisma, TypeORM; `InMemoryReadModelStore` in a project without an ORM), declared with `@Repository(<Name>)` or bound in the module file in the explicit style, the fake, and `test/integration/<name>.contract.spec.ts`, which runs `readModelContract` on the fake and on the adapter. `--field <name>:<string|number|boolean|instant|decimal>[:nullable]` adds a field to the row, to the criteria, to the table and to the columns of the adapter at once; `--tenant-scoped`, or a multi-tenant project, gives the table its tenant column and the store the scope of the work. The column of a field accepts null whatever the row requires, a removed row being a trace that keeps its key and its stamp alone, and a check constraint `<table>_live_rows_whole` keeps every other row whole: `check(...)` on Drizzle, `table.check(...)` on Knex, `checks` of the entity schema on TypeORM; the schema language of Prisma has none, so its model carries a `TODO(domain)` line with the `ALTER TABLE` to add to the migration. `generate projection` names the command in its file and in a note, `generate adapter` refuses the port of a read model with it, and the `persistence`, `scaffold` and `wiring` skills of the plugin say it. A repository generated after a read model in the same context finds the imports of its own table (`integer`, `auditColumns`), and a table may bear the name of a column of another.
