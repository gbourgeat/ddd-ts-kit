**Two first saves of one aggregate made at once are a lost update on a table with a unique column too, never a unique violation for the value they both write.** On PostgreSQL, the first save of an aggregate inserted with the key alone as its conflict target (`ON CONFLICT (id) DO NOTHING`). Two inserts of the same id made at once (a request delivered twice, a command run again while its first run commits) both pass the check of the key, then meet on the other unique index of the table (an email, a number), and the one that lost was answered `UniqueViolationError` (code `CONFLICT`, 409) for a value no other row held, where `optimisticUpdate` promises `ConcurrencyError` (code `CONCURRENCY_CONFLICT`). `insertIgnoringConflict` of `@ddd-ts-kit/knex` and of `@ddd-ts-kit/typeorm` now inserts with a statement that skips on any unique value, and only when it wrote nothing with a second one that names the key: a key that is held writes no row, and a value another row holds is still refused by the database, with the error of the driver as the cause of the `UniqueViolationError`. `@ddd-ts-kit/drizzle` gains the same helper, `insertIgnoringConflict(() => executor.insert(table).values(row), table)`, which says whether it inserted, and `generate repository` and the identity preset write it on Drizzle in place of `onConflictDoNothing({ target: primaryKeyOf(table) })`. A repository on `@ddd-ts-kit/prisma` was not concerned: `skipDuplicates` names no target and `rowsCreated` tells a taken id from a taken value. `repositoryContract` of `@ddd-ts-kit/testing` gains the case, with the new option `createAggregateAgain`: the same new aggregate saved several times at once, one save that writes it and the others refused with `CONCURRENCY_CONFLICT`. The stores of the kit were not concerned: their tables hold no second unique value two writers of one key could both write. See [Persistence](docs/tools/persistence.md).

To move: nothing on Knex and TypeORM, whose repositories call the helper. On Drizzle, `grep -rn "primaryKeyOf(" src` lists the first saves to take up: `insertion.onConflictDoNothing({ target: primaryKeyOf(table) }).returning(...)` becomes `insertIgnoringConflict(() => this.database.executor().insert(table).values(row), table)`, which answers a boolean where the statement answered its rows (`? 1 : 0` under `optimisticUpdate`). Give `createAggregateAgain` to the `repositoryContract` of a repository over a table with a unique column, and run it on a real PostgreSQL: one connection, as PGlite has, never crosses two inserts.
