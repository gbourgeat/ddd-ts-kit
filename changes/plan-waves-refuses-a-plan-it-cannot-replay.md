**`plan-waves` exits 1 while the generator refuses a planned command, whatever the reason, with the refusal under the row, and while a row builds on what a row it does not wait for generates.** A plan whose commands the generator refused for another reason than a word (a missing `--module` in a context divided into modules, `--grant` on a project whose rights are relationships or attributes, an aggregate no earlier row generates, an unknown flag) passed with those commands listed apart, and plans were committed with most of their commands refused when followed as written. Each such command is now a problem of the plan, `refused-command`, reported without waves like a word the glossary does not define: the command as the row writes it, the refusal and the fix of the generator printed under the row, and, when the generator refused it for what it builds on (an aggregate, a port, a use case, a route or a controller, a route group, the job that starts the use case of an end-to-end spec, a codec of stored events, a repository that declares personal data, a context, an upstream, the declaration of an event), which row generates that, found by running the command again with `--dry-run` once the whole plan has run, every file it builds on in one pass: a later row it does not wait for (add it to `Depends on`, each such row named), a later row that waits for it (move the command, rather than make a cycle), a later command of the same row (put it first), or none as the rows are written (add the command, or fix the refused row that would generate it), with what the command is refused for then, for another reason or for another file no row generates (`nextRefusal`, a `--grant` once the aggregate is found). The generator now says, while it replays a command, which files it builds on and which it creates, so a command that builds on a file a row it does not wait for generates is refused too, as a `missing-dependency`, even when that row comes first and the replay, one row after the other in one copy, found the file: the worker of the row, on a branch of its own, would not; a command also refused names that row with its refusal, one problem per command. A row `in progress` is still replayed, so that the rows after it find what it generates, but neither its names, nor its refusals, nor the rows it builds on are counted: its worker may have added the term a name needs on their branch, its commands may have run in the project already, and the generator refuses a second run of some of them (a port already bound to an adapter); they are listed apart with their fix, under `Refused in rows in progress, not counted` (`started` in `--json`). `--json` gives a refused command its `command`, `refusal`, `fix` and `prerequisite`, a missing dependency its `command` and `builtOn`, and no longer has `notReplayed`. The `plan-slices` and `parallel-work` skills say to fix the row as the refusal says. `generate` itself now reads its kind after a leading flag that takes a value (`generate --module pricing job catalog Reprice --every 15m --command RepriceAll` is a job), where it took the value of the flag for the kind.

To move: a plan committed with refused commands, or with a row that builds on what a row it does not wait for generates, now fails `npx ddd-ts-kit plan-waves`: fix each row it names (add the `--module`, drop the `--grant`, add the row that generates the aggregate or the context to `Depends on`) until it exits 0. A reader of `--json` reads the refused commands from `problems` (`kind: "refused-command"`) instead of `notReplayed`.
