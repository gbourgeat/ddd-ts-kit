**`plan-waves` exits 1 while the generator refuses a planned command, whatever the reason, with the refusal under the row.** A plan whose commands the generator refused for another reason than a word (a missing `--module` in a context divided into modules, `--grant` on a project whose rights are relationships or attributes, an aggregate no earlier row generates, an unknown flag) passed with those commands listed apart, and plans were committed with most of their commands refused when followed as written. Each such command is now a problem of the plan, `refused-command`, reported without waves like a word the glossary does not define: the command as the row writes it, the refusal and the fix of the generator printed under the row, and, when the generator refused it for what it builds on (an aggregate, a port, a use case, a route group), which row generates that: a row the plan runs later that the row does not wait for (add it to `Depends on`), a later command of the same row (put it first), a row the generator refuses too, or none (add the command). A row `in progress` is still replayed, so that the rows after it find what it generates, but its refusals are not counted: its commands may have run in the project already, and the generator refuses a second run of some of them (a port already bound to an adapter). `--json` gives the problem its `command`, `refusal`, `fix` and `prerequisite`, and no longer has `notReplayed`. The `plan-slices` and `parallel-work` skills say to fix the row as the refusal says.

To move: a plan committed with refused commands now fails `npx ddd-ts-kit plan-waves`: fix each row it names (add the `--module`, drop the `--grant`, add the row that generates the aggregate to `Depends on`) until it exits 0. A reader of `--json` reads the refused commands from `problems` (`kind: "refused-command"`) instead of `notReplayed`.
