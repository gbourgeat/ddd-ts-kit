**Breaking: `ReadModelStore.updateIfNewer` changes a row another event created, and throws the event back while that row is not there.** A projection wrote such an event (an appointment moved, a payment captured) as an `upsertIfNewer` whose `next` answered `undefined` when the key held no row. Delivered before the older creation it follows, the change was `ignored` and acknowledged; the creation then wrote the row as it was at first, and the change was lost for good. `updateIfNewer(key, stamp, change)` of `@ddd-ts-kit/kernel`, where `change` takes the row and answers the row, is the write for that event: `applied` on a row the key holds, `stale` when the row, or the trace of its deletion, holds this event or a later one, and `RowNotHeldError` (which carries the `key`) when the key holds no row, or the trace of a deletion older than the event, since a row deleted then changed was created again in between and that creation has not been applied yet. Nothing is written, and the error is meant to leave the projection: the unit of work of the event rolls back with its processed mark, the provider delivers the event again, and it is applied after the creation. It is retried and dead-lettered as any failed event, so a change whose creation never comes ends in the dead letters of its provider; `projection_events_total` of `@ddd-ts-kit/di` counts each such delivery under a result of its own, `early`, not `failed`. `TableReadModelStore`, so the stores of `@ddd-ts-kit/knex`, `@ddd-ts-kit/drizzle`, `@ddd-ts-kit/prisma`, `@ddd-ts-kit/typeorm` and `@ddd-ts-kit/opensearch` and `InMemoryReadModelStore`, and `ShadowReadModelStore` have it; during a rebuild the key of a refused change is still read again from the source. `upsertIfNewer` keeps its meaning: `next` answering `undefined` is a filter, for an event the read model has no row for and never will. `readModelStoreContract`, `readModelRowsContract` and `readModelContract` of `@ddd-ts-kit/testing` hold the cases, "a change delivered before its creation is refused, then applied after it" among them; `generate projection` of `ddd-ts-kit` names the two writes in the method it leaves to fill. See `docs/concepts/cqrs.md`, "Which write for which event".

To move: a class of your own that extends `ReadModelStore` without extending `TableReadModelStore` implements `updateIfNewer`. In each projection, replace `upsertIfNewer(key, stamp, (row) => (row === undefined ? undefined : { ...row, ... }))` by `updateIfNewer(key, stamp, (row) => ({ ...row, ... }))` where the event changes a row another event of the projection creates, and let `RowNotHeldError` leave the method (no `try`); keep `upsertIfNewer` where answering `undefined` filters an event that has no row here. A spec that expected `'ignored'` for a change without its row expects the rejection. Size the retries of the consumer for the delay a late creation can take, and read a dead letter with the code `RowNotHeldError` as a creation that never came. A dashboard that sums the results of `projection_events_total` meets `early`.
