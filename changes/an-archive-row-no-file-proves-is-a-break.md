**An archive row that no file proves is the break of its chain.** The guard of the trail lets through the `DELETE` of an entry a row of `audit_archives` covers, so a role that may both insert such a row and delete entries can let entries go behind a row of its own. `verifyTrail(trail, { files })` now reads back the file of every archive of each chain, oldest first, and proves it with `verifyArchive` against the one before it, before it verifies the entries left from the anchor of the last: a row without its file answers `missing-entry`, a file that does not prove its row `altered-content`, at the first sequence the row names, and a storage that fails to give a file back `unreadable-archive`, a new kind of `ChainBreakKind`, for that chain alone. Whatever the storage, the rows follow each other with no gap and the head goes on from the last one: a head behind it, or at its end with another hash, is a break. `VerifyAuditTrail(trail, files)` passes the storage on. A generated project with a storage of files gives it to the nightly `audit.verify` and to `npm run audit:verify`. The documentation of the guard says which two privileges open that path, and that they belong to the role that archives.
