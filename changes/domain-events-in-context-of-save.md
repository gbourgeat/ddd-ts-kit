**The handlers of a domain event run in the execution context of the save that recorded it, so an integration event published for a command run inside another one carries the tenant of the inner command.** A command dispatched inside another joins its unit of work, and its domain events are dispatched at the end of the outer one: their handlers ran in the execution context of the outer command, and what they published took its tenant, or none when the outer work had none, so the consumers answered `FORBIDDEN` or worked in the wrong tenant. `dispatchingOnSave` and `announceDomainEvents` of `@ddd-ts-kit/kernel` take the execution scope as an optional last argument and keep, with each event, the context in progress at the save; both phases (`before-commit`, `after-commit`) run in it. `kernelModule` of `@ddd-ts-kit/di` passes the scope it binds, and the platform `init` writes without a container passes its own.

To move: under a container, nothing. In a project assembled by hand (`"stack.di": "manual"`), in `src/platform/composition/create-platform.ts`, pass the scope to `adapterOf` and write `dispatchingOnSave(resilient, () => domainEvents, () => scope)`. A handler that relied on running in the context of the outer command reads the execution context of the save instead.
