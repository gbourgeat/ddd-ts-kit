**A background job declares the schema of its payload, and the worker reads every stored payload with it before the run: one that does not fit is dead with `INVALID_JOB_PAYLOAD`, never run.** A payload waits in the queue (the jobs table, Redis, the memory of the process) across deploys; until now the worker handed it to the typed `run` as it was stored, so a job enqueued before a deploy that changed its shape ran as the new type, a missing field read as `undefined`. A background job class now carries a static `payload` next to its `jobName`, a `BackgroundJobPayloadSchema` of the kernel (`parse(input)` answering a `Result`), which the `Schema` of `@ddd-ts-kit/validation` is, whatever library it adapts. It is required by the types: `jobs.enqueue(Job, ...)`, `@Background()`, `builder.backgroundJob(..).handledBy(Job, ...)` and `platform.backgroundJobs.register(Job, ...)` do not compile without it, `handledByFactory(factory, payload)` takes it, `BackgroundJobDefinition` of `@ddd-ts-kit/scheduling` has `payload`, and at run time `@Background()` throws `DeclarationError` and a module `WiringError` (`INVALID_JOB_SETTINGS`) for a class without one. Before each run `QueueWorker` parses the stored payload and hands `run` what the schema answers; a payload it refuses fails the attempt with `InvalidJobPayloadError` (code `INVALID_JOB_PAYLOAD`, its message naming the job, the id of the stored job and the path and code of each issue, `issues` holding them with their messages), and the job is dead at once, no retry: `find` shows `dead` with that code, the log and the metrics carry the code, `reportFailedBackgroundJobs` sends it to the error reporter, and an operator retries it (`retryDead`) once a version that reads it is deployed. The timeout job of a process uses `processTimeoutDuePayload` of the kernel. `generate background-job` writes the schema in the validation library of the stack (a `z.object` under zod, a class of decorated fields without initial value under class-validator, a `Type.Object` under TypeBox, one refusal per field written by hand under Standard Schema and, with `--validation none`, in the form of the kernel), the type of the payload inferred from it, and its spec enqueues the job as an earlier version typed it (`const earlierVersion: BackgroundJobType<unknown> = MyBackgroundJob`) and shows the job dead. `layer/application-inward` lets a background job, `application/background/*.background-job.ts` and no other file of the layer, import `@ddd-ts-kit/validation` and the validation library of its schema, in `ddd-ts-kit check`, the ESLint plugin and the dependency-cruiser file. [Background jobs](docs/concepts/background-jobs.md) says how to evolve a payload: a new field is optional, a new shape is a new job name.
