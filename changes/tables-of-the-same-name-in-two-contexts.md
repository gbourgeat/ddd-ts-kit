**Two contexts may hold a table of the same name on Drizzle and on TypeORM.** `ddd-ts-kit generate read-model billing InvoiceSummaries` then `generate read-model shipping InvoiceSummaries`, or two aggregates of one name stored in two contexts, or the identity preset beside a context that holds `accounts`, wrote a schema index (`src/platform/database/schema.ts`) that named the same constant twice: the project did not compile, and on Drizzle the migration `db:generate` wrote, like the test database, left out the tables of the second context without a word. The two tables never met in the database, each being in the schema of its context, and they still do not; Knex and Prisma were not concerned. The index now settles the name: the context that held it first keeps it, and the second is listed under a name that carries its context, `export { invoiceSummaries as shippingInvoiceSummaries } from` on Drizzle beside `export { invoiceSummaries } from` for the first, `import { invoiceSummaries as shippingInvoiceSummaries }` on TypeORM. The tables file of a context, its stores and its repositories keep the name of the table. The same holds for a table that bears the name of one the index declares itself, `jobs`, `outbox`, `processes`: on Drizzle the aggregate `Job` of a context compiled, and its table was never created, the constant of the index hiding it; it is now listed as `billingJobs`. The name the second table takes is one nothing holds: where `shippingOrders` is the table `shipping_orders` of a context, or `shippingSchema` the schema constant of the context, it is `shippingContextOrders`, then `shippingOrders2`.

What is settled. A name two tables files of contexts export, each its own table, or one the index declares itself: each command that writes the index (`generate`, `init --force`, `merge-trunk`) writes the lines by name the whole index lacks, not only those of the context it works for, in the `// ddd-ts-kit:schemas` region, one name a line. What is compared is a symbol, the file that declares it and its name, each file by the path it is read at, a context laid out in modules (its tables file in `shared/`) as a flat one: two tables files that re-export one table of the shared kernel hold one symbol, whether one names the file through the alias of the project and the other by a relative path, which `export *` brings as before, and nothing is written nor said. Where the index gives a shared name to nothing yet, the context it re-exports first keeps it; a generator leaves it to the other context only for the name its command brings, and `merge-trunk` gives it to the table the trunk exports under it when the kit settles it, whatever the order of the index and whatever the layout of a context on either side: each side is read as its commit lays its contexts out, flat or in modules, so a table that moved to `shared/` on one side is the same table on the other, and the merge says nothing of it unless a line still names the old place. A name that has a value in a tables file, a table beside the type of its rows (`export const invoices` and `export type invoices`), an enum and the type of its values, a class and an interface, is exported from it with a plain `export { ... }` line, which carries the type too; `export type { ... }` is written only for a name that is a type and no value in that file. `default` is never settled. After the lines are written the kit reads the index again: every value of every file it re-exports whole must be exported as a value under a name, or the lines are taken back. The sentence `lists the name ... as ...` is printed for each line that was written.

What is only said. `generate` and `init --force` compare what the index gave before the command with what it gives after: on Drizzle the table each name exports, on TypeORM the entities `entities` lists, as far as the kit reads them. A table within reach before and under no name after, or listed no more, or a name that exported one table and would export another, leaves the index as it stood before the command: the comparison is made once, when every generator of the command has run, on the state the command ends in. The index is listed under `left` and in `skipped` of the report, never in `updated`, and the command exits 3. One note names every table concerned and says what would have been lost or moved; `generate` gives the lines it wrote, to write by hand, when it wrote some, and ends with what leaving them out costs when the `export *` line of a context is among them (its tables are listed nowhere, no migration will create them); `init --force` gives none: the line that keeps the table belongs in the `// ddd-ts-kit:schemas` region, which the rewrite keeps, and until it is moved there every `init --force` leaves the index as it stood. A table `generate --force` drops from a tables file it writes again whole is said in a note, on Drizzle and on TypeORM (where the index, which still imports it, does not compile), and the command exits as it would without it: the index is not left for that. A name that did not compile before, two `export *` bringing it, exported nothing: settling it is no such change. `generate` refuses, before it writes anything, a table whose name the tables file of the context already exports from another file. `ddd-ts-kit init --force` writes the index again from its template, which drops what a team wrote outside the `// ddd-ts-kit:` regions; it leaves the index as it stood on disk, with one note, when that would lose a table a file it re-exports or names holds, or give such a name to another table, and when the part outside the regions holds something it does not read with certainty (on Drizzle an `export` it does not answer for or a module re-exported whole it does not follow; on TypeORM an entry of `entities` the rewritten list lacks, unless it is a constant the index builds by calling a function imported from a package of the kit: that one is taken for a line of a template and goes with the rewrite, as before) and the rewrite would drop a line written there. Apart from that rewrite, no command removes a line of the Drizzle index: the line of a table that is gone is a compile error to fix by hand. On TypeORM an import is removed only when the entity is imported under two names in the region the kit writes and each name has its entry in `entities`: one import and its entry go, the other name stays listed.

`ddd-ts-kit merge-trunk` settles the names the two sides share between tables files of contexts, in lines of the shape the kit writes, and says so under `automatic:`, in a dry run too, which reads the files the merge reads. A line or an import of the merged index that names the place a side held a context's tables file at, which the merged tree no longer holds because the other side moved the file (`context-layout` laying the context out in modules), is not written again: the index is left as the merge wrote it, a compile error as before, and the report says each such line, in the dry run too: `` `export { orders } from '...'` names '<old place>', which the merged tree no longer holds: billing's tables file is now '<new place>'; write that path in the line``. While such a line is there, the kit writes no name nor any other line of that merge, on Drizzle and on TypeORM, and says it once. A file counts as moved only when the merged tree holds no file at its old place. When it holds both, one side having laid the context out in modules while the other stored a table flat, the context has two tables files, and on Drizzle what follows applies; a file counts as a tables file only when it declares a value of its own, so a flat file that only re-exports the one of `shared/`, or an empty one, is none. When the two files declare no name in common, the merge goes on as any merge. When they declare one (the schema of the context first), the kit writes no name, nor any other line of that merge, and says it once: it names the two files and the names both declare, and says what must hold once a person made them one file, the one of `shared/`: every table of the flat file there, on the schema it declares; for a table name both declare, the one of the two files the trunk's index exports it from, under that name or another, keeps it (the sentence names that file and the name the trunk gives it) and the other takes a new name in every file that imports it; a schema constant both declare is kept once, the tables of the flat file built on the one of `shared/`; the flat file and the `export *` line that names it gone, every other import and line of the index pointed at `shared/`; then a commit and `npx ddd-ts-kit init --force`. The report still names each table hidden and each name moved, as in any merge. On TypeORM the merge says nothing of the two files: an entity both files export under one name stays imported twice, which does not compile, and the note says to write the second import `<name> as <another name>` by hand; other names of that merge are settled as in any merge. When the merge stops on a conflict, the sentences about the names come at `--continue`, once; the dry run gives them in advance. A name the trunk exports keeps naming the table of the trunk when the line that gave it to another table on the branch is one the kit wrote, one name a line; any other shape (a line by hand with several names, a module that is no tables file of a context) is not repaired. Whatever it wrote, the report then says, the dry run as the merge: each table a side had within reach, still in the merged tree, that the merged index exports under no name, with its file and the name that hides it; and each name of the trunk or of the branch that names another table after the merge, when the table it named is still re-exported whole (`export *`) by the merged index. When the kit does not read a side or the merged index with certainty, cannot write the index, or would give a name of the trunk to another table, it writes nothing and says why, with the lines to write by hand except in that last case. An error while it settles the names is said in the report and never leaves the merge in progress. On TypeORM the merge settles entities only in an index the kit wrote whole: a line it did not write, anywhere in the index, keeps it from renaming or taking out any import, and the merge quotes that line (`<index>: the kit wrote nothing for the entities: the index holds a line the kit did not write (line <n>: ...)`). In an index the kit wrote whole, an entity each side imported and listed under its own name keeps the name the trunk gives it and is listed once; the import of the branch that goes is recorded in the merge commit, only once every entity the merged index listed is still listed, else the index is left as the merge wrote it. Each text the settle of a merge writes in the index that the index did not hold before is recorded in a `Kit-Written:` trailer of the merge commit, and the lost-lines check never counts it as a line of the merge's own, so a line a careless resolution lost elsewhere in the index still stops the merge, as on main; every line the settle takes out is recorded in `Lost-Accepted:` by its file, its side and its text (`<file>@<side>#<hash>`), so it never accepts a loss of the other side at the same place. A `Lost-Accepted:` entry written as `file` or `file:line`, by a person or an earlier version, is read as before.

What the kit reads. A module the index re-exports whole is the tables file of a context when it resolves to that file, whatever its name looks like; any other file of the project is read for what it is and keeps the names it exports, and a table of a context that bears one of them is listed under the name of its context. In a file it reads a declaration of one name (`export const orders = ...`, a function, a class, an enum, a type), a list (`export { orders }` of a name the file declares at its top level or imports by name), a name taken by name from any module (`export { held as orders } from './tables'`: from a file of the project it reads, what that file exports under it; from a package or a module it does not find, that name, a value unless written as a type), and the files of the project a file re-exports whole. What a file declares or takes by name wins over what a module it re-exports whole brings under the same name, as in the language. When something is not read with certainty and the index lacks a line for a name shared among what was read, the kit writes nothing and a note gives the lines to write by hand, `the kit wrote no name in it: ...`; an index without its region gets every line, the `export *` line of the context first. A command prints at most one such note, or the note of an index left as it stood. Nothing is printed when no name is shared among what was read, except when a name a tables file exports is written, as a word of the code, comments and strings left out, in a file of the project that is not read with certainty or in an `export` of the index that is not read: the note gives the line that names it apart.

`ddd-ts-kit init --force` settles an index that holds both under one name (on TypeORM, a name two tables files are imported under), says what it settled, and says what to write by hand for an import it cannot rewrite. `drizzle-generate` warns that a migration drops two tables an unsettled index lists under one name, `typeorm-generate` no longer takes the entity of one context for the entity of the same name of another when it warns of dropped tables, an entity imported under an alias through a file of its context or a barrel of it is read as listed, and `verify-slice` stages an index whose only changes are the statements that name the tables file of its context, the entries of what they import, and the line that lets the tables file of another context keep a name it holds and the slice came to share, an import written on several lines included; a line of the platform that only mentions a table of the context leaves the index out.

Limits. The kit resolves a module specifier by the aliases of `ddd-ts-kit.config.json` and relative paths, to a `.ts` file or the `index.ts` of a folder; it does not read `paths` of `tsconfig.json` beyond those aliases, `baseUrl`, nor the `package.json` of a folder, and where the compiler could read something else (a file and a folder of one name, a `.tsx`, a `.d.ts`, a `.js`, an `.mts` or a `.cts` beside or in place of the `.ts`, a folder that holds a `package.json`) the specifier resolves to nothing. A file is not read with certainty when it holds one of these, and a name shared with it is then not settled, the names the other files share still are when the index itself is read: two names declared in one statement, a pattern (`export const { orders } = tables`), a `declare` of a value, a default export, a module exported as a name, a name with a character outside letters, digits, `_` and `$`, a regular expression literal or a template that does not close (a division is sometimes read as a regular expression), a `namespace` or `declare module` block, two modules re-exported whole that bring different things under one name, a package re-exported whole, or a module re-exported whole that resolves to nothing. What such a module re-exported whole holds is not looked into: a name it shares with another file through `export *` does not compile, as before, and one a line by name of the index already gives to something else stays hidden without a word. A table already hidden by a line a team wrote by hand, in favour of a file that is no tables file of a context, is not reported. On TypeORM the names of the imports are local to the index: in a merge the import of the trunk keeps its name and the one of the branch is renamed. On TypeORM the merge settles entities only in an index the kit wrote whole: a line it did not write, anywhere in the index, keeps it from renaming or taking out any import, and the merge quotes that line. The kit wrote the index whole when, outside its regions, it holds the text the template of `init` writes for the flags of the project, whitespace aside; in `// ddd-ts-kit:imports`, imports by name (`import { orders, orders as shippingOrders } from '...';`, on one line or several) of a tables file of a context or of a package of the kit; in `// ddd-ts-kit:schemas`, bare names each followed by a comma, blanks allowed around either, the shape the kit also takes out. Any other line, a comment included, is a line of the team, whatever it reads: the kit writes nothing for any entity, the index stays as the merge wrote it (two imports of one name do not compile, as before), and one sentence gives the first such line and its number. When that line stands outside the regions, most often a line of the template of an earlier version, the sentence ends with what makes the next merge settle: `npx ddd-ts-kit init --force` after a commit writes the index again from the template of this version, and settles the names then. The sentence comes only when there is something to settle, two imports of the region under one name or one entity under two names there; `init --force` settles under the same rule. The kit tells two entities apart only by the tables files that declare them: a name re-exported, renamed or aliased in a tables file is not settled, and the merge says so. An import counts as an entity the kit may settle only when its specifier resolves to the tables file of a context that declares the name itself, a constant built by `new` in the statement that exports it, at the top level (`export const orders = new EntitySchema(...)`, or a top-level `const orders = new ...` that `export { orders }` lists under that name), written with semicolons or without; its identity is that file and that name. Any other import of a shared name (a re-export of any kind, `export * from './billing-tables'` included, a renamed export, a constant alias of another binding, a module that resolves to nothing, a package) gets nothing written for the name and one sentence, `imports \`orders\` twice and the kit cannot tell the entities apart: '<file>' does not declare \`orders\` itself; the kit wrote nothing for it: import each entity from the tables file that declares it`. Two imports of one name that bind the one entity of the file that declares it (`@/contexts/shipping/...` beside `../../contexts/shipping/...`, or one specifier twice) get nothing written, as before (the index does not compile), and the sentence `imports the entity \`orders\` of shipping twice under one name; the kit wrote nothing for it: take out one of the two imports`; the entity is never listed twice. A name is told apart only in one shape: two imports of the region under that name, of two different entities neither of which the region imports under another name, and one entry; an entity imported under two names is listed once only when it has exactly those two imports, each name listed once. Any other shape of a name (three imports or more, one entity twice, two entries or more) gets nothing written and one sentence, `imports \`orders\` 3 times (...) and lists it once; the kit wrote nothing for it: keep one import of each entity, each under its own name, and list each name once`. What the settle leaves is then checked: every entity it touched imported under one name listed once in `entities`, no name it touched listed twice, no name moved to another entity, no entry left without the import that gives its name; else the index is put back as it stood, and one sentence says what would have been wrong. On TypeORM a merge that leaves two tables files for a context says nothing of them: an entity both files export under one name stays imported twice, which does not compile, and the note says to write the second import `<name> as <another name>` by hand; other names of that merge are settled as in any merge. On TypeORM the list of the entities is read as the names between the brackets of `entities`, comments left out: an entry is an entity when a name imported in the index bears it, and a spread or a constant built elsewhere is not followed. `init --force` keeps the lines outside the regions only by leaving the whole index as it stood, in the cases above; any other line written there goes with the rewrite, as before. A settle that `generate` refuses leaves the new tables out of the index until the lines of its note are written. On Drizzle, when the merged tree holds two tables files for a context that declare a name in common, no name of that merge is settled and no line rewritten; `init --force` afterwards gives a shared name to the context the index re-exports first, which may not be the trunk's. A table the index declares itself outside the regions (`export const legacyOrders = pgTable(...)`) is not in what `init --force` compares: it goes with the rewrite without a word, as before, and a name it held may then name the table of a context. On TypeORM a tables file that builds its entity with `new` of a class returning another object is taken for its own entity: the kit cannot see through it.

To move: nothing in a project that compiles and whose tables are all created. A project on Drizzle or TypeORM whose index names one table twice runs `ddd-ts-kit init --force` after a commit, which settles each name and says so, unless the note says the index was left as it stood, which says why, then `npm run db:generate <name>` (`npm run build && npm run db:generate migrations/<name>` on TypeORM) to write the migration of the tables that were left out. A project on Drizzle that stores an aggregate whose table bears a name the index declares, `Job` (`jobs`) or `Process` (`processes`), compiled on 0.112.0 and never created that table: it runs the same two commands. A script that reads the `Lost-Accepted:` trailers of merge commits now meets entries of the form `<file>@<side>#<hash>` beside `<file:line>` and `<file>`, and a new `Kit-Written:` trailer: it reads them as entries it does not know, or skips them.
