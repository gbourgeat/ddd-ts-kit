**The guard of the plugin no longer refuses three commands a worker may run inside its scope.** A folder of its context is moved, removed and copied into (`git mv <folder>`, `mv`, `rmdir`, `rm -r`, `cp file <folder>/`): the guard took a folder for a file with another name (a hard link), since a folder counts more than one link. The folder of the context itself is inside the scope for a tool given it whole (`eslint src/contexts/<context> --fix`). The schema of a query string, `presentation/http/<resource>/<use-case>/*.query.ts`, is written by hand as `docs/ARCHITECTURE.md` says, in the presentation layer of a context alone (`<context>/presentation/`, `<context>/<module>/presentation/`, `<context>/shared/presentation/`): everywhere else a new `*.query.ts` is still sent to `generate query`. A command given a folder (`cp`, `mv`, `ln`, `install`, `rsync`) is judged by what it brings into it and by the files it lands on there: a link or a whole tree comes from the scope alone, a file named lands where its name leads, and a whole tree, or files whose names the shell computes, land in no folder that holds a file with another name elsewhere, nor in one past 5000 files. `chmod`, `chown`, `chgrp`, `chattr`, `chcon`, `chflags`, `setfacl`, `setfattr`, `git add --chmod` and `git update-index --chmod` are held to the scope as a command that writes the file is. And the words of the command behind a package runner (`npx`, `pnpx`, `bunx`, `npm exec`, `pnpm exec`, `pnpm dlx`, `bun x`) are read as the shell split them, so `npx ddd-ts-kit generate value-object invoicing SupplierName --term "SupplierName=le nom d'un fournisseur"` is no longer refused as a quote that never closes, nor a `>` or a `;` inside a quoted word read as a redirection or a second command. That holds for the one shape the guard reads in full: the runner, its subcommand, the options it knows (`-y`, `-p`, `-w`, `--filter`, `--dir` and their like), then a program named plainly and its arguments. Any other invocation may hand text to a shell (`-c`, `--call`, `--shell-mode`, an option the guard does not know, short options written together, `true` or `false` after an option that takes no value, `npm exe`, a setting such as `npm_config_call` on the line, `yarn`, `bun run`) and every word of it is read as shell text, as before. A runner told where to run (`pnpm -C <dir> exec`, `npm --prefix <dir> exec`, `bun --cwd <dir> x`) has its command judged in that directory, `pnpm <program>` is read as `pnpm exec <program>`, and a worker runs no command in another checkout, where it only reads. A wrapper (`time`, `nice`, `timeout`, `env`, `sudo` and their like) is read through to the command it runs when the guard knows each option it is given; behind any other first word that is no program the guard knows, each later word that may name a program is read as a command too. A wrapper that writes a file of its own (the report of `time -o`, the log of `strace -o` or `script`, the lock of `flock`, `nohup.out` when nothing takes the output) is held to the scope for it as a redirection is, one given an option the guard does not know may write anywhere and is refused, and a wrapper or a program told where to run (`env -C <dir>`, `sudo -D <dir>`, `make -C <dir>`, `npm --prefix <dir> run`, `pnpm -C <dir> install`) is judged there, as a command after `cd <dir>;` is.
