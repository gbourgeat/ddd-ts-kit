**On a PostgreSQL server (`DATABASE_URL`), each end-to-end spec file of a generated project runs on a database of its own, copied from the migrated one, so the files run at the same time and two runs at once no longer block each other.** Until now every file shared the database the URL names and emptied its tables in `reset()`: the files had to run one after the other (`fileParallelism` off under Vitest, one worker under Jest), two runs started together could end in a deadlock on `truncate` (40P01), and the audit trail, which nothing empties, carried the rows of the other files. `openTestDatabase(url)` of the four ORM now creates a database from the migrated one (`create database ... template`), connects the persistence to it and drops it at `close()` (`drop database ... with (force)`); the new `test/support/test-database-clone.ts` does it for all four. `reset()` still empties the tables of the copy between two tests, the audit trail starts empty in each file, and the migrated database is never written by a test. `vitest.e2e.config.ts` and `jest.e2e.config.js` no longer read `DATABASE_URL`: they keep the files one after the other only where a server is still one for every file, a broker (`AMQP_URL`, `KAFKA_BROKERS`, `NATS_URL`) or a Redis protocol server (`REDIS_URL`). A server that was never migrated is refused with `npm run db:migrate` in the message instead of `relation does not exist`, and so are a role that may not copy the database and a migrated database somebody else is connected to. A copy is named `<database>_test_<seconds of its date>_<random>`; the ones a killed run left are dropped by the next file that starts, an hour later, and no database with another name ever is. See [the testing strategy](docs/concepts/testing-strategy.md).

What changes on the server: the role of `DATABASE_URL` needs `CREATEDB` and owns the migrated database, or is a superuser (the role of the generated `docker-compose.yml` and of the generated pipelines is one), the server is PostgreSQL 13 or later, and nobody else may be connected to the migrated database while a file starts (an application left running on it, a console): PostgreSQL copies a database only then.

To move: these files are written once by `init`, so a project already generated takes them by hand. Generate a project with the same flags in a temporary directory (`npx ddd-ts-kit init` with the `stack` of your `ddd-ts-kit.config.json`) and copy from it: `test/support/test-database-clone.ts` (new); in `src/platform/database/open-test-database.ts`, the import of `cloneDatabase` and the function `openServer`, which connects to `clone.url` and ends its `close` with `await clone.drop()`; in `vitest.e2e.config.ts`, the `fileParallelism` line, removed, or kept on the broker and Redis variables alone; in `jest.e2e.config.js`, `sharedServer` and `maxWorkers`, the same way. Then, where the role is not a superuser, let it create databases and own the migrated one (`alter role <role> createdb`, `alter database <database> owner to <role>`). A spec of your own that connects to `DATABASE_URL` itself now holds a session on the migrated database and makes the other files fail: connect it to the `postgres` database, or read through the application.
