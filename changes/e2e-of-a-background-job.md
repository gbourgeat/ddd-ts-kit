**`ddd-ts-kit generate e2e` writes the end-to-end spec of a use case a background job starts, and the end-to-end support runs what is due on the queues.** `generate e2e <context> <UseCase>` found a route, then an integration event handler, then a scheduled job, and refused a use case only a background job sends the command of. It now finds the background jobs of the context too (`application/background/*.background-job.ts`) and writes a spec in three steps: the request whose use case enqueues the job, to send through the API (a `TODO(domain)`), `const ran = await application.runDueJobs()`, then `application.settled()` and what a client observes. The spec asserts that the job is among `ran`, so it fails until the request that enqueues is written. A use case a scheduled job and a background job both send gets one test per job. `--job <JobName>` names one job, scheduled or background, by its class (`VoidInvoice`, `VoidInvoiceBackgroundJob`) or by the name it runs under (`billing.void-invoice`), also for a use case a route reaches: that spec is written in `test/e2e/<use-case>-<job>.e2e.spec.ts`, beside the one of the route; `--event` and `--job` together are refused.

`runDueJobs()` is new in `test/e2e/support/start-application.ts`, next to `runJob(name)`, which runs a scheduled job at once: it stops the worker of the process (a queue kept in memory starts one, and a job it claimed would end behind the spec), runs every job due until none is left on the worker of the application, answers the name of each job run, and rejects when a run did not succeed, naming the job, its outcome and the code of its error, never the message. On a container it resolves the `QueueWorker` of the kernel module; where the platform is wired by hand, or under Nest, it calls `platform.backgroundJobs`, which gains `runDue()` (`src/platform/jobs/background-jobs.ts`, `create-background-work.ts`). It is the same on the three queue stores (`memory`, `database`, `redis`). A project on a container lists `@ddd-ts-kit/scheduling` in its development dependencies when its queue does not already list it at run time: the support imports the token of the worker from it. The `testing`, `scaffold` and `integration-event` skills of the plugin say it, with the pages [testing strategy](docs/concepts/testing-strategy.md) and [background jobs](docs/concepts/background-jobs.md).

To move: nothing has to change. `init` keeps the support of an existing project as it is, and `generate e2e` notes what it lacks when a spec needs it. To add `runDueJobs` by hand: declare `runDueJobs(): Promise<string[]>;` on `RunningApplication`, and implement it on the worker, `application.container.resolve(QueueWorker)` on a container (`QueueWorker` of `@ddd-ts-kit/scheduling`, to add to the development dependencies if the project does not list it), or `application.platform.backgroundJobs` by hand once `runDue: () => worker.runDue()` is among what `backgroundJobsOn` of `src/platform/jobs/create-background-work.ts` answers and `runDue(): Promise<BackgroundJobRun[]>;` is on the `BackgroundJobs` interface: `await worker.stop()`, then `const runs = await worker.runDue()`, throw when the `outcome` of a run is not `succeeded`, and answer `runs.map((run) => run.job)`.
