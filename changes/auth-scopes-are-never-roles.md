**The scopes of a token are never roles, the system role is held by a system actor only, and a token without `exp` is refused.** The default mapping of `JwtAuthenticator` and `actorOfClaims` fell back on the `scope` claim when a token carried neither `realm_access.roles` nor `roles`, so a token whose `scope` held `admin` was an administrator under the generated `roles.ts`; it now reads `realm_access.roles`, else `roles`, and a token that carries only scopes gives an actor with no role (the scopes stay in `session.scopes`, which `HasScope` reads). `RoleBasedAuthorizer` gave a user whose roles named the `systemRole` what the system holds; that role is now left out of the roles of any actor but a system one, and `explain` says so (`<role> is the role of the system, held by a system actor only`). `JwtAuthenticator` (and `keycloakAuthenticator`) refuses a signed token without `exp` with the reason `NO_EXPIRY`, unless given `requireExpiry: false`, a conscious choice for an issuer whose tokens never expire. `DEFAULT_JWT_ALGORITHMS`, exported by `@ddd-ts-kit/auth`, is the allow-list of `JwtAuthenticator` (RS256, PS256, ES256, EdDSA). The `bearer-strategy.ts` that `init --authn passport` writes refuses a token without `exp` too, with the same `requireExpiry` option, and its comment names `DEFAULT_JWT_ALGORITHMS` as the source of its RS256, PS256 and ES256: `jsonwebtoken`, under `passport-jwt`, cannot verify EdDSA, so an EdDSA issuer needs `--authn jwt`.

To move: a provider whose tokens carry only scopes, with roles meant to come from them, maps the roles itself with `toActor` (`JwtAuthenticator`) or in `actor-of-token.ts` (`--authn passport`); a token without `exp` is now refused, so issue tokens with `exp` or set `requireExpiry: false`; a user or service that held the system role through its token loses it, give it a role of its own. A project generated with `--authn passport` keeps its `bearer-strategy.ts`: to refuse a token without `exp`, copy `requireExpiry` and `carriesExpiry` from a new `init --authn passport`.
