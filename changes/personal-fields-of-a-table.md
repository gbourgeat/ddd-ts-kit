**`ddd-ts-kit generate personal-fields <context> <table> --personal <column>,... --subject <column>` declares the personal data of a table no aggregate owns.** A read model, a table of received messages or a table written by hand in the schema of a context had no generator: `generate repository --personal` asks for an aggregate, so their `*.personal-fields.ts` and their lines in the erasure and the export adapters were written by hand. The new generator takes the SQL name of a table the schema file of the context declares (Drizzle, Knex, Prisma, TypeORM), writes `infrastructure/persistence/<table>.personal-fields.ts` spelled as the erasure of the ORM reads it, and joins it to the erasure and the export of the context, or writes them when the table is the first (ports, adapters, fakes, binding, the copies and the exports of the platform, and a spec that proves the fakes and names each case to prove on the test database as `it.todo`, no repository nor builder writing the rows of such a table). `--subject` is required there: the row is rarely the person, and a default of `id` would have `privacy:erase` miss it. The table is never changed: a table the schema does not declare, a table that has a declaration, a column the table does not hold and, where the erasure is confined to a tenant, a table without `tenant_id` are refused; a column that could not be read (the definition spreads shared columns) is said in the output. `--erasure`, `--retention`, `--tenant-scoped` and `--module` as on a repository. The refusal of `generate repository <context> <Aggregate> --personal ...` on a table that exists now names this command, and so does the fix of `privacy/declared-field`.
