**A class the kit writes for class-validator refuses an input that lacks one of its fields.** A field was written with an initial value (`calendarId = ''`, `refundAmount = 0`, `notifyCustomer = false`), which class-transformer keeps for a field the input lacks: a request without `calendarId` passed `@IsString()` as if it carried an empty one, and a consumer read an integration event without it the same way. Each field is now `declare`d with no initial value (`declare calendarId: string;`), and an optional one is `@IsOptional()` with `declare note?: string;`. This covers the body, path parameter, `Accepted` and `Line` classes `generate route` writes (functions, controllers and Nest routes), the body fields it reads from the constructor of the command, the payload of `generate integration-event`, the optional fields of the payload of `generate background-job` (its required ones already were), and the DTOs and payloads of `init --preset identity`. The spec `generate route` writes for a route that reads its body from the command now sends that body without its first field and expects 422 `VALIDATION_FAILED` with the issue at `body.<field>`, whatever the validation library. The `TODO(domain)` of an empty class-validator class says to `declare` its fields, and `privacy/event-payload-declared` reads a `declare`d member of a payload class, which it skipped.

To move: rewrite each decorated field of your class-validator DTOs and payloads without an initial value, `@IsString() calendarId = '';` becoming `@IsString() declare calendarId: string;` (and `@IsOptional() declare note?: string;` for an optional one); a field whose absence means a default is made `@IsOptional()` and the route reads it with `?? <default>`. Left as it is, a request or an event that lacks the field keeps passing.
