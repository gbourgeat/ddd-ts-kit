**Breaking: a deletion in a read model leaves its trace under a key the table does not hold, and a deleted row keeps no data.** `ReadModelStore.delete(key, stamp)` of `@ddd-ts-kit/kernel` on a key the read model did not hold wrote nothing and answered `ignored`, so a deletion delivered before the older creation it follows let that creation make a row that should not exist, and a rebuild lost a deletion made while it exported a row it had not copied yet. It now inserts the trace (the key, the stamp, `deleted`, the tenant of a read model of tenant data) and answers `applied`; the older creation is then `stale`. `ignored` is left to an `upsertIfNewer` whose `next` answers `undefined`. On `@ddd-ts-kit/knex`, `@ddd-ts-kit/drizzle`, `@ddd-ts-kit/prisma` and `@ddd-ts-kit/typeorm`, a deleted row now holds NULL in every column of the row, as it already kept nothing in memory and on `@ddd-ts-kit/opensearch`: its personal data is gone and a unique value it held is free again. So every column of the row is nullable, and a table that is not ready is refused by name, `ReadModelTableNotReadyError`, which lists the columns and gives the check constraint: when the store is built on Drizzle and TypeORM, from the definition, and on the four before the first trace is written, from one read of the columns the database holds, never by a statement that would abort the transaction of the event. On TypeORM and Prisma, an insert that takes a unique value another row holds is no longer skipped in silence: only a conflict on the key is, and the other is refused, by the database on TypeORM, with `UniqueViolationError` on Prisma. `readModelStoreContract` and `readModelRowsContract` of `@ddd-ts-kit/testing` hold it, with two capabilities to give them: `stored(key)`, which reads the table beside the store, and `uniqueTitle`. A read model of tenant data keeps its keys unique across tenants: under a key another tenant holds, a deletion stays `ignored`, and an upsert is now refused at once with `ReadModelKeyHeldElsewhereError`, a `ConcurrencyError` that says the key should carry the tenant, where it spent five attempts first. See `docs/concepts/cqrs.md`, "The table of a read model, and what a deleted row leaves".

To move: for each read model table, write a migration that drops NOT NULL on every column of the row (not on the key, the tenant column, `last_event_id`, `last_event_at`, `deleted`) and keeps the live rows whole: `alter table <table> alter column <column> drop not null` for each, then `alter table <table> add constraint <table>_live_rows_whole check (deleted or (<column> is not null and ...))` over the columns that were NOT NULL; `update <table> set <column> = null, ... where deleted` empties the rows deleted before. Declare the same in the definition the store reads: no `.notNull()` on Drizzle, `nullable: true` on TypeORM, optional fields (`String?`) on Prisma. A unique index `WHERE NOT deleted` may become a plain one. A statement of your own on the table keeps filtering `deleted = false`. Code that counts an `applied` deletion as a row removed (an erasure that reports what it reached, and tells a mistyped id from a run again by it) asks `get(key)` first and deletes only what it finds: `applied` now also answers a trace written under a key never held. A `ReadModelRows` of your own now inserts an entry without a `row` (the trace) where it answered `false`, and writes no data on a replace without one. Run `readModelStoreContract` again on your stores: the table of its dataset needs the same migration.
