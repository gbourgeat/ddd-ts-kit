**Breaking: a deletion in a read model leaves its trace under a key the table does not hold, and a deleted row keeps no data.** `ReadModelStore.delete(key, stamp)` of `@ddd-ts-kit/kernel` on a key the read model did not hold wrote nothing and answered `ignored`, so a deletion delivered before the older creation it follows let that creation make a row that should not exist, and a rebuild lost a deletion made while it exported a row it had not copied yet. It now inserts the trace (the key, the stamp, `deleted`, the tenant of a read model of tenant data) and answers `applied`; the older creation is then `stale`. `ignored` is left to an `upsertIfNewer` whose `next` answers `undefined`. On `@ddd-ts-kit/knex`, `@ddd-ts-kit/drizzle`, `@ddd-ts-kit/prisma` and `@ddd-ts-kit/typeorm`, a deleted row now holds NULL in every column of the row, as it already kept nothing in memory and on `@ddd-ts-kit/opensearch`: its personal data is gone and a unique value it held is free again. So every column of the row is nullable, and a table that is not ready is refused by name, `ReadModelTableNotReadyError`, which lists the columns and gives the check constraint: when the store is built on Drizzle and TypeORM, before the first trace is written on Knex and Prisma (one read of the columns), never by a statement that would abort the transaction of the event. `readModelStoreContract` and `readModelRowsContract` of `@ddd-ts-kit/testing` hold it, with two capabilities to give them: `stored(key)`, which reads the table beside the store, and `uniqueTitle`. A read model of tenant data keeps its keys unique across tenants: a deletion under a key another tenant holds now ends in a `ConcurrencyError`, as an upsert did, where it was ignored. See `docs/concepts/cqrs.md`, "The table of a read model, and what a deleted row leaves".

To move: for each read model table, write a migration that drops NOT NULL on every column of the row (not on the key, the tenant column, `last_event_id`, `last_event_at`, `deleted`) and keeps the live rows whole: `alter table <table> alter column <column> drop not null` for each, then `alter table <table> add constraint <table>_live_rows check (deleted or (<column> is not null and ...))` over the columns that were NOT NULL; `update <table> set <column> = null, ... where deleted` empties the rows deleted before. Declare the same in the definition the store reads: no `.notNull()` on Drizzle, `nullable: true` on TypeORM, optional fields (`String?`) on Prisma. A unique index `WHERE NOT deleted` may become a plain one. A statement of your own on the table keeps filtering `deleted = false`. Code that deletes a key in every tenant in turn (an erasure) first asks `get(key)` and leaves alone a tenant that holds nothing. Run `readModelStoreContract` again on your stores: the table of its dataset needs the same migration.
