**Generated code names an error code by a constant, which the editor completes and the compiler checks, where it wrote a string.** `@ddd-ts-kit/kernel` exports `KitCodes`, the codes the packages of the kit raise (`KitCodes.Forbidden` is `'FORBIDDEN'`, `KitCodes.ValidationFailed` is `'VALIDATION_FAILED'`, and so on for the twenty-two of them), with the type `KitCode`. The generators write it wherever they named such a code: the `errors` of a function route (`errors: [KitCodes.Unauthorized, KitCodes.Forbidden]`), of a route group (`errors: [KitCodes.Forbidden]`), of a guard and of the audit routes of the platform, the spec of a route or of a controller (`code: KitCodes.ValidationFailed`), the specs of the handlers (`rejects.toMatchObject({ code: KitCodes.Forbidden })`), of a search reader and of a value object, and the route groups and the handler specs of the identity preset. Under `"stack.refusals": "named"`, the spec `generate error` writes for a refusal expects its code by its entry of the code list of the context (`expect(error.code).toBe(BillingCodes.InvoiceAlreadyIssued)`), and a spec written before is given the import of the list when a case is added to it.

What reads an `errors` list reads both forms. `errors/known-code` follows a member of a code list to its code: the list of the context of the route (`<context>.codes.ts`), that of the shared kernel, or `KitCodes`; it reports a key the list does not hold, a code of another context named through the list of that context, and a member of anything else, which it cannot read. `ddd-ts-kit describe`, the reference of `CONTEXT.md` and the digest give the code a member names. `ddd-ts-kit controllers` leaves out of a controller the codes of the kit its guard and its group already say, written either way, and writes the group with `KitCodes.Forbidden`.

`expectProblem` and `expectRefusal` of `@ddd-ts-kit/testing` take the codes a caller names as a type argument: `expectProblem<SchedulingCode | KitCode>(response, { status: 409, code: 'SLOT_TAKEN' })` and `expectRefusal<SchedulingCode>(() => appointment.cancel(at), 'APPOINTMENT_ENDED')` refuse a code outside them at compile time. Without the type argument they take any string, as before.

Left as it was: under `"stack.refusals": "factories"` and `"classes"` a context has no code list, so its own codes stay strings; the identity preset still writes the codes of its context as strings in its controllers and its specs.

To move: nothing has to change, a string still names its code. To take the constants in a project already generated, import `KitCodes` from `@ddd-ts-kit/kernel` and replace each code of the kit written as a string in `errors: [...]` and in the specs (`'FORBIDDEN'` becomes `KitCodes.Forbidden`, `'VALIDATION_FAILED'` becomes `KitCodes.ValidationFailed`); under named refusals, replace a code of the context by its member of `<Context>Codes`. A route that already named a code through an object of its own (`errors: [MyCodes.Something]`) is now reported: `ddd-ts-kit check --rule errors/known-code` lists them, and each is written as a member of the code list of its context, of `KitCodes`, or as a string.
