**Breaking: `ReadModelTableNotReadyError` says what is missing and writes the migration, and is built from what it reports.** Its message named the table and the columns that refuse NULL, then gave the statement to write with a `<column>` to fill in. It now names the table, the columns, what is known of the check constraint `<table>_live_rows_whole` (missing, or there without these columns, or, when a definition was read and not the database, what to declare there) and the whole migration as PostgreSQL statements: `alter table ... alter column ... drop not null` for each column, `add constraint ... check (deleted or (...))` when the constraint is missing, and the `update ... set ... = null where deleted` that empties the rows deleted before. The statements are also in its `migration` field, what it reports in `unready` (an `UnreadyReadModelTable`: `schema`, `table`, `refusing`, `row`, `constraint`), and `readModelTableMigration(unready)` of `@ddd-ts-kit/kernel` answers them alone. Before its first trace, a store of `@ddd-ts-kit/knex`, `@ddd-ts-kit/drizzle`, `@ddd-ts-kit/prisma` and `@ddd-ts-kit/typeorm` reads the constraint of a table it refuses, one more statement on that path only. `table` and `columns` keep their meaning.

To move: code that builds the error itself (a `ReadModelRows` of your own) passes the object, `new ReadModelTableNotReadyError({ schema, table, refusing, row })`, where it passed `(table, columns)`; a test that compared the whole message compares its first sentence, or `table` and `columns`.
