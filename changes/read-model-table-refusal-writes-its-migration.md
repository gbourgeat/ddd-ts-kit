**Breaking: `ReadModelTableNotReadyError` says what is missing and writes the migration in two steps, for the columns its store maps and no other, and is built from a `ReadModelTableState`.** Its message named the table and the columns that refuse NULL, then gave the statement to write with a `<column>` to fill in. It now names the table, each thing that keeps it from holding a trace, and the whole migration as PostgreSQL statements, in its `steps` field (`definition`, then `validation`) and, both in order, in `statements`. The state it reports is the reading of the store (`PostgresTraceColumns` of `@ddd-ts-kit/kernel`, behind the tables of `@ddd-ts-kit/knex`, `@ddd-ts-kit/drizzle`, `@ddd-ts-kit/prisma` and `@ddd-ts-kit/typeorm`), which looks at the columns the store maps as fields of its row and at nothing else: the key, the tenant column whatever its name, the stamp and a column the store does not map are never read, never altered and never emptied. Among the mapped columns it tells those that refuse NULL (`refusing`) from those no migration opens (`unfit`: a part of the primary key, an identity column, a generated column, a column of a domain that refuses NULL, a column that is not there), and says when the table itself is not in the database; a store whose mapped column is unfit refuses, with no statement for that column, where it failed later on the database. The stamp columns carry the names the definition of the store gives them, so a renamed `deleted` column is the one the migration names; on TypeORM, the names the naming strategy of the data source gives the table and its columns.

The first step is the change of definition, one statement: NOT NULL dropped on each refusing column and, in the same `alter table`, the constraint `<table>_live_rows_whole` written again, `not valid`. Nothing commits between the two, on any migration tool. Before it changes anything, the statement reads the constraint the database holds under that name and fails on one that is not written as the kit writes it: a constraint of the project that happens to carry the name is never dropped, on the database that was read or on another. The second step validates the constraint and empties the rows deleted before, with an update that touches only the rows still holding a value. Every identifier is quoted, the statements hold no backslash and no question mark (a string of JavaScript and `knex.raw` carry them as they are), and the migration can be run twice. The name of the constraint is cut at 63 bytes, as PostgreSQL cuts it, not at 63 characters.

The first step takes the lock that stops the readers and the writers of the table, and holds it to the end of its transaction. On a small table both steps go in one migration. On a large one the second step goes in a migration that runs outside the transaction of the first, where the validation and the update stop neither readers nor writers, and each tool needs something for that: knex runs every pending migration in one transaction unless the second ends with `export const config = { transaction: false };`; TypeORM does unless the data source says `migrationsTransactionMode: 'each'`; Drizzle always does, so the second migration is added and applied after the first; Prisma commits each statement of a file except a file with a `do` block, which the first step is, so two migrations. `docs/tools/persistence.md`, "A large read model table: the second step apart", gives each case as it was run, with the locks read in `pg_locks`.

The constraint is read exactly: only the form the kit writes, as PostgreSQL prints it back, counts as holding columns; `(deleted or title is not null) and ..` or `deleted or not (..)` under that name is another check. A constraint that is not validated, another check under that name, and any other check constraint that names a column of the row are read and reported as warnings by `ReadModelTables`, not as refusals: nothing in the columns refuses a trace, and the kit does not decide what an arbitrary check does. A refusal read from a definition alone (Drizzle, TypeORM, a column declared not null there) carries no statement and says to declare the column nullable.

To move: code that builds the error itself (a `ReadModelRows` of your own) passes a state, `new ReadModelTableNotReadyError({ table, exists: true, refusing, unfit: [], row, deleted: 'deleted' })` (`schema` and `constraint` when known), where it passed `(table, columns)`; a test that compared the whole message compares `table`, `columns`, `steps` or `statements`. A read model whose store maps a part of its primary key, an identity column, a generated column or a column of a domain that refuses NULL as a field of its row is now refused before its first trace: take that column out of the fields the store maps, or make it an ordinary nullable column. A TypeORM entity without `tableName` is named in a refusal by the table the naming strategy gives it (`strict_row`), not by its entity name.
