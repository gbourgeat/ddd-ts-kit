**Events of one key applied at once to a read model are no longer refused for another unique value of its table.** A read model table that holds a second value unique (a unique index on a slug, a number) could refuse one of two writes of the same row made at once, on PostgreSQL, with the unique violation of that other index: the insert named the key alone as its conflict target, and two inserts that cross meet on the other index first. No write was lost, since the handler of the event failed and the event is delivered again, but the error named a value no other row held. The stores of `@ddd-ts-kit/drizzle`, `@ddd-ts-kit/knex` and `@ddd-ts-kit/typeorm`, and on `@ddd-ts-kit/prisma` the copy of a rebuild (its model already skipped on any unique value), now insert with a statement that skips on any unique value, and only when it wrote nothing with a second one that names the key: a key that is held is compared with the event and written if the event is newer, and a value another row holds is still refused by the database. `readModelStoreContract` and `readModelRowsContract` of `@ddd-ts-kit/testing` gain the cases, for a storage that says `uniqueTitle`: writers that insert one row at once, in the table and in the copy of a rebuild, and several rows that take one unique value at once, of which one holds it and the others are refused. See [CQRS](docs/concepts/cqrs.md).

To move: nothing for a table of the four ORM. A `ReadModelTable` of your own that runs the contract with `uniqueTitle` and holds the value in memory takes it before its write, as an index does, and gives it back when nothing was written: checked after the write, two rows inserted at once both pass.
