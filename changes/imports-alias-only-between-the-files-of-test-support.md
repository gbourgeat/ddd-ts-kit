**`imports/alias-only` lets a file directly under `test/support/` import its neighbour by `./<name>`.** A test runner loads its global setup, and every file that one imports, before any alias of the project exists: Jest applies no `moduleNameMapper` there. A global setup made of several files could therefore import them by alias only when the runner was started under a loader that resolves aliases, and failed with `Cannot find module '$test/support/...'` from `NODE_OPTIONS=--experimental-vm-modules npx jest` or from the runner of an editor. The rule, in `ddd-ts-kit check` and in `@ddd-ts-kit/eslint-plugin`, now leaves that one relative path alone: from a file directly under `test/support/`, a specifier `./<name>` that names a neighbour file. Nothing else changes: from `test/support/`, `../e2e/support/start-application`, `./parts/part`, `./.`, `./..` and a `./parts` that is a directory are reported as before, and a file of any other directory still imports its neighbour by alias. The rule judges how that path ends, and `eslint --fix` rewrites it: with no extension under `"importExtension": "none"`, with the `.ts` of the source under `"js"` (`./test-database-run.ts`), since the runner loads the sources and a `./test-database-run.js` there passes the type check, then stops the run on `Cannot find module`. `init` writes what lets the type check of such a project read that ending, and `imports/alias-declared` holds it. See [Import aliases](docs/tools/import-aliases.md).
