**The read model tables an application lists are checked when it starts and, from the command line, before a deployment, each by its own store.** A table that cannot hold the trace of a deleted row was refused when its store was built (Drizzle, TypeORM) or before its first trace (the four ORM). In an application whose container builds a store at its first use, both came with the first request or the first event that reached the read model, in production, one table at a time, and nothing listed the tables an upgrade left to migrate. A `TableReadModelStore` of `@ddd-ts-kit/kernel` now answers `tableState()`, the reading its table makes before its first trace (`tableState()` of the `ReadModelTable` port, implemented by the table of `@ddd-ts-kit/knex`, `@ddd-ts-kit/drizzle`, `@ddd-ts-kit/prisma` and `@ddd-ts-kit/typeorm`), as a `ReadModelTableState`. `ReadModelTables` of the kernel takes a list of functions that each build a store and asks it of each: `states()`, `notReady()`, `require()` (which refuses with `ReadModelTablesNotReadyError`, one error that names every table with its migration), `atStart(logger, 'required' | 'reported')` for a start and `report()` for a command. The verdict is the one of the store by construction: the same table, schema, columns and stamp names, read by the same code, so a table is found ready exactly when its store takes a trace, and a table nobody lists is never read, whatever else the database holds. An empty list checks nothing and says nothing; a store without a table (memory, OpenSearch) has nothing to say. `readModelTablesContract` of `@ddd-ts-kit/testing` holds the four ORM to it on PostgreSQL.

A project generated by `ddd-ts-kit init` on one of the four ORM has the list in `src/platform/database/read-model-tables.ts`, between the markers `// ddd-ts-kit:imports` and `// ddd-ts-kit:read-model-tables`: `ddd-ts-kit generate read-model` adds the store it writes, `init --force` keeps what is between them, and a store written by hand is added by hand. The application checks the list when it starts, before a consumer is subscribed or a request served: the platform module on tsyringe, InversifyJS and Awilix, `start` of `compose-application.ts` on a platform wired by hand, so the worker, a service and the end-to-end tests check too. A listed table that is not ready stops the start, which in a rolling deployment keeps the old instances serving until the migration ran; a pipeline that starts the application before its migrations passes `readModelTables: 'reported'` to `composeApplication`, and the same message is logged as one error. `npm run db:read-models` (`scripts/read-model-tables.ts`) runs the same check on the database `DATABASE_URL` names and needs no other variable of the application: it prints how many tables it read and their names, then each one that is not ready with its migration, and exits 0 when all are ready, 1 when one is not, 2 when `DATABASE_URL` names no database, 3 when the database could not be read. Since the list is a file every context shares, `generate read-model` on an ORM is a step of the conductor under `--local-only`. The persistence skill of the plugin says when to run the command and what to do with its refusal. See `docs/concepts/cqrs.md`, "Every table checked at the start, and before a deployment".

To move: a project generated before gets the check by hand, or by `ddd-ts-kit init --force`, which writes `src/platform/database/read-model-tables.ts` with an empty list (and keeps the list of a file that has the markers), `scripts/read-model-tables.ts`, the call of the start and the script of `package.json`; the stores generated before are then added to the list by hand. By hand:

1. `src/platform/database/read-model-tables.ts`:

```ts
import { ReadModelTables, type ReadModelInATable } from '@ddd-ts-kit/kernel';
import type { Persistence } from '@/platform/database/persistence';
// ddd-ts-kit:imports
import { KnexAgenda } from '@/contexts/scheduling/infrastructure/persistence/knex-agenda.repository';
// /ddd-ts-kit:imports

const LISTED: readonly ((persistence: Persistence) => ReadModelInATable)[] = [
  // ddd-ts-kit:read-model-tables
  ({ database }) => new KnexAgenda(database),
  // /ddd-ts-kit:read-model-tables
];

export function readModelTables(persistence: Persistence): ReadModelTables {
  return new ReadModelTables(LISTED.map((build) => () => build(persistence)));
}
```

One line per read model kept in a table, built as the application binds it; a store of tenant data takes any execution scope as its second argument (`new AsyncLocalStorageExecutionScope()` of the kernel), which the check never reads.

2. The start. On a container, in the platform module, `onStart: ({ resolve }) => readModelTables(persistence).atStart(resolve(Logger), options.readModelTables),`. On a platform wired by hand, `readonly readModelTables: ReadModelTables;` in the `Platform` interface, `readModelTables: readModelTables(persistence),` where the platform is created, and `await platform.readModelTables.atStart(platform.logger, options.readModelTables);` in `start` of `compose-application.ts`, before `options.events.start()`. In both, `readonly readModelTables?: ReadModelTablesAtStart;` in `PlatformOptions`.

3. In `package.json`, `"db:read-models": "tsx --env-file-if-exists=.env scripts/read-model-tables.ts"`, and `scripts/read-model-tables.ts`, which opens the persistence on `process.env['DATABASE_URL']` alone (`openPersistence({ databaseUrl })`), prints `(await readModelTables(persistence).report()).text`, sets `process.exitCode` to 1 when `ready` is false, and closes the persistence.

Before the next deployment, `DATABASE_URL=<its database> npm run db:read-models` lists what is left of the 0.111.0 migration.
