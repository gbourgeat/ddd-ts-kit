**Every read model table is checked when the application starts and, from the command line, before a deployment, whatever builds its stores.** A table that cannot hold the trace of a deleted row was refused when its store was built (Drizzle, TypeORM) or before its first trace (the four ORM). In an application whose container builds a store at its first use, both came with the first request or the first event that reached the read model, in production, one table at a time, and nothing listed the tables an upgrade left to migrate. `knexReadModelTables(context)` of `@ddd-ts-kit/knex`, `drizzleReadModelTables` of `@ddd-ts-kit/drizzle`, `prismaReadModelTables` of `@ddd-ts-kit/prisma` and `typeOrmReadModelTables` of `@ddd-ts-kit/typeorm` answer a `PostgresReadModelTables` of `@ddd-ts-kit/kernel`, which reads the catalog of the database in one statement, no row and no lock, and needs no store: a read model table is known by its stamp (`last_event_id`, `last_event_at`, `last_event_version`, `deleted`, the names `readModelColumns` gives on every ORM), and its row is every other column but the primary key and `tenant_id`. `notReady()` answers every table that is not ready, `require()` refuses with `ReadModelTablesNotReadyError`, one error that names them all with the migration of each, and `atStart(logger, 'required' | 'reported')` is the check of a start. `readModelTablesContract` of `@ddd-ts-kit/testing` holds the four on PostgreSQL, the written migration run included. A project generated by `ddd-ts-kit init` on one of the four ORM calls it at the start of the application, before a consumer is subscribed or a request served: `src/platform/database/read-model-tables.ts`, called by the platform module on tsyringe, InversifyJS and Awilix (declared and explicit styles) and by `start` of `compose-application.ts` on a platform wired by hand, so the worker, a service and the end-to-end tests check too. It is on by default, since it costs one statement: a table that is not ready stops the start, which in a rolling deployment keeps the old instances serving until the migration ran. A pipeline that starts the application before its migrations passes `readModelTables: 'reported'` to `composeApplication`: the same message is logged as one error and the start goes on. `npm run db:read-models` (`scripts/read-model-tables.ts`) runs the same check on the database `DATABASE_URL` names and exits 1 when a table is not ready: on the database of an environment before its deployment, or after `npm run db:migrate` on an empty one to judge the migrations. It is a script of the project, which reads through its ORM, since the CLI has no database driver; no check reads the migration files, whose four forms say less than the database they make. A column no store writes NULL in (one the store does not map and the database fills, a tenant column named otherwise) is named in `{ kept: ['<schema>.<table>.<column>'] }`. A read model on OpenSearch or in memory has no such table and nothing to check. See `docs/concepts/cqrs.md`, "Every table checked at the start, and before a deployment".

Before the next deployment, `new ReadModelTablesNotReadyError(await readModelTables(persistence).notReady()).message` in a script run against its database lists what is left of the 0.111.0 migration.
