**The read model tables an application lists are checked when it starts and, from the command line, before a deployment, each by its own store and each root for the contexts it hosts.** A table that cannot hold the trace of a deleted row was refused when its store was built (Drizzle, TypeORM) or before its first trace (the four ORM). In an application whose container builds a store at its first use, both came with the first request or the first event that reached the read model, in production, one table at a time, and nothing listed the tables an upgrade left to migrate. A `TableReadModelStore` of `@ddd-ts-kit/kernel` now answers `tableState()`, the reading its table makes before its first trace (`tableState()` of the `ReadModelTable` port, implemented by the table of `@ddd-ts-kit/knex`, `@ddd-ts-kit/drizzle`, `@ddd-ts-kit/prisma` and `@ddd-ts-kit/typeorm`), as a `ReadModelTableState`. `ReadModelTables` of the kernel takes a list of entries, each a name and what builds a store, and asks it of each: `states()`, `notReady()`, `require()` (which refuses with `ReadModelTablesNotReadyError`, one error that names every table with its migration), `atStart(logger, 'required' | 'reported')` for a start and `report()` for a command. The verdict is the one of the store by construction: the same table, schema, columns and stamp names, read by the same code, and a table nobody lists is never read, whatever else the database holds. Every entry is tried: one whose store cannot be built, or whose table the database refuses to read (a role without the right to use the schema), is told under its name with its cause, in `unread` of the same error, the others are still read, and `'reported'` logs it and lets the start go on. What the check cannot decide is a warning at the start and a line of the command: a check constraint that is not validated or is not written as the kit writes it, another check constraint that names a column of the row, a view, a store the application names as not listed. A store without a table (memory, OpenSearch) has nothing to say. `readModelTablesContract` of `@ddd-ts-kit/testing` holds the four ORM to it on PostgreSQL.

A project generated by `ddd-ts-kit init` on one of the four ORM has the list in `src/platform/database/read-model-tables.ts`, between markers: an entry is the context of a read model and the class of its store, `['billing', KnexInvoiceSummaries]`, and the context is one of those the file holds in `Contexts`, which `generate context` fills, so an entry under a misspelt name does not compile. `ddd-ts-kit generate read-model` adds the store it writes, under an alias that carries its context when another context holds a store of that class name. `init`, with or without `--force`, adds the read model stores the tree holds and the list does not, so a project generated before the list existed gets it filled; it reads every class of the persistence of each context, several in one file and a store over a base class of the project included; a store it cannot list with certainty (its own constructor is not `(database)` nor `(database, scope)`, or is inherited; a generic class) is named in a note and in `NOT_LISTED` of the file, and the check says at each start that nothing checks its table. A store left out on purpose is a comment of the list that holds `<context>: <Store>` and the reason: `init` leaves it out and nothing warns of it, where an entry merely deleted comes back at the next `init --force`. An application checks, when it starts and before a consumer is subscribed or a request served, the entries of the contexts it hosts: the whole application and the worker every context but those run as services, a service (`generate service`) its context alone, so each root starts on a database that holds its own tables. A listed table that is not ready stops the start, which in a rolling deployment keeps the old instances serving until the migration ran; a pipeline that starts the application before its migrations passes `readModelTables: 'reported'` to `composeApplication`, and the same message is logged as one error. `npm run db:read-models` (`scripts/read-model-tables.ts`) runs the same check on the database `DATABASE_URL` names, for every context or for those `-- --context <name>` names, and needs no other variable of the application: it prints the database it reads (name and host, never credentials, since a `.env` file may give the address), how many tables it read and their names, then each one that is not ready with its migration, and exits 0 when all are ready, 1 when one is not, 2 when `DATABASE_URL` names no database, 3 when no table could be read, 4 when `--context` names a context no listed read model belongs to, with the contexts the list holds. Since the list is a file every context shares, `generate read-model` on an ORM is a step of the conductor under `--local-only` (`docs/guides/parallel-work.md`). The persistence skill of the plugin says when to run the command and how to write the migration of its refusal, and the parallel-work skill names the new conductor step. On TypeORM, the table and the columns of a refusal, the mark of a deleted row included, are named as the database holds them under the naming strategy of the data source. See `docs/concepts/cqrs.md`, "Every table checked at the start, and before a deployment", which also says what the check does not read (a trigger, a rule, a check of a domain, the table under a view).

By hand instead:

1. `src/platform/database/read-model-tables.ts`:

```ts
import {
  AsyncLocalStorageExecutionScope,
  ReadModelTables,
  type ExecutionScope,
  type ReadModelInATable,
} from '@ddd-ts-kit/kernel';
import type { Persistence } from '@/platform/database/persistence';
// ddd-ts-kit:imports
import { KnexAgenda } from '@/contexts/scheduling/infrastructure/persistence/knex-agenda.repository';
// /ddd-ts-kit:imports

type Store = new (database: Persistence['database'], scope: ExecutionScope) => ReadModelInATable;

type Contexts = [
  // ddd-ts-kit:contexts
  'scheduling',
  // /ddd-ts-kit:contexts
];

const LISTED: readonly (readonly [context: Contexts[number], store: Store])[] = [
  // ddd-ts-kit:read-model-tables
  ['scheduling', KnexAgenda],
  // /ddd-ts-kit:read-model-tables
];

const NOT_LISTED: readonly string[] = [
  // ddd-ts-kit:read-models-not-listed
  // /ddd-ts-kit:read-models-not-listed
];

export function readModelTables(persistence: Persistence, contexts?: readonly string[]): ReadModelTables {
  const scope = new AsyncLocalStorageExecutionScope();

  const listed = LISTED.map(([context, Store]) => ({
    context,
    name: Store.name,
    build: () => new Store(persistence.database, scope),
  }));

  return new ReadModelTables(listed, NOT_LISTED).hosting(contexts);
}
```

One line per read model kept in a table: the name of its context, as `ddd-ts-kit.config.json` declares it, and the class of its store. The scope is given to a store of tenant data and never read by the check.

2. The start. On a container, `platformModule` takes the hosted contexts as a third parameter, `hosted?: readonly ContextModule[]`, reads their names (`const contexts = hosted?.map(({ name }) => name);`), its module holds `onStart: ({ resolve }) => readModelTables(persistence, contexts).atStart(resolve(Logger), options.readModelTables),`, and `compose-application.ts` calls `platformModule(persistence, options, contexts.modules)`. On a platform wired by hand, `readModelTables(contexts: readonly string[]): ReadModelTables;` in the `Platform` interface, `readModelTables: (contexts) => readModelTables(persistence, contexts),` where the platform is created, `start: () => start(platform, options, contexts),` in `composeApplication`, a third parameter `hosted: readonly ContextWiring[]` of `start`, and `await platform.readModelTables(hosted.map(({ name }) => name)).atStart(platform.logger, options.readModelTables);` there, before `options.events.start()`. In both, `readonly readModelTables?: ReadModelTablesAtStart;` in `PlatformOptions`.

3. In `package.json`, `"db:read-models": "tsx --env-file-if-exists=.env scripts/read-model-tables.ts"`, and `scripts/read-model-tables.ts`, which opens the persistence on `process.env['DATABASE_URL']` alone (`openPersistence({ databaseUrl })`), refuses with exit code 4 a `--context` that is not among `readModelTables(persistence).contexts`, prints `(await readModelTables(persistence).hosting(contexts).report()).text`, sets `process.exitCode` from `outcome` (`ready` 0, `not-ready` 1, `unread` 3), and closes the persistence.
