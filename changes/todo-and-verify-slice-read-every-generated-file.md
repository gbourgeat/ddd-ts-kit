**`todo` reads the markers of every kind of file, `prisma/schema.prisma` included, and `verify-slice` stages the schema and the behaviour pages the generator wrote for the slice.** `ddd-ts-kit todo <context>` read only the TypeScript and Markdown files of the context: the `TODO(domain)` that `generate repository` leaves in `prisma/schema.prisma` (the columns of the new model) went unnoticed, and the row was committed with it. `todo` now reads the schema of Prisma, under the context whose database schema holds the model (`todo <context>` lists it), and, for the whole project, the migrations (`migrations/`, `prisma/migrations/`), the pages under `docs/` and the configuration at the root (`docker-compose.yml`, the config files of the ORMs, `ddd-ts-kit.config.json`), not the lockfiles. The other ORMs already wrote that marker in the tables file of the context, which `todo` read. `status`, `story-check` and the state of a worker count the same markers. `verify-slice` listed `prisma/schema.prisma` and `docs/behaviour/*` as left out, for a person to decide about, while the generator and `regenerate` had written them for the slice. It now stages the pages of `docs/behaviour/` (the page of the context, the application and the index, but not the page of another context), and `prisma/schema.prisma` or the schema index of the platform (`<platformDir>/database/schema.ts`, for Drizzle, Knex and TypeORM) when every line changed there since `HEAD` is of the context: a model of its database schema and that schema joining the datasource, or the import of its tables file. A change of another model in the same file keeps it left out. The working migration of a Prisma worker (`prisma/migrations/<number>_working_<what>/migration.sql`) is staged like those of the other ORMs.
